估计一个算法要跑多久往往很有用。当然，可以直接实现并运行它，但这里会出现问题：

- 在不同计算机上运行时间总是不同。
- 不总能预先拿到它实际要运行的那些数据。
- 有时需要估计耗时数小时甚至数天的算法。
- 生命短暂，如果有多个算法可选，想提前预测哪个更快，从而只实现它。

为此，作为第一近似，我们尝试估计算法中*操作的个数*。问题来了：到底该算哪些操作。一个方案是考虑所有基本操作：

* 数的算术运算：`+, -, *, /`
* 数的比较：`<, >, <=, >=, ==, !=`
* 赋值：`a[0] = 3`

重要的是不要只数行数，还要考虑语言里某些东西是怎么实现的。例如，Python 中数组切片（`array[3:10]`）会复制数组，也就是说这个切片要 7 次基本操作。而 `swap` 例如可以用 3 次赋值实现。

**练习。** 试着在[排序](../sorting)（冒泡、选择、插入、计数）最坏情况下数出*比较*和*赋值*的精确个数。这应是某个依赖于 $n$（数组长度）的公式。

要把所有基本操作都考虑进去，还得数例如 `for` 循环里 1 加了多少次。还有，例如 `n = len(array)` 这行也算一次操作。因此即使数出来了，也不立刻清楚哪个算法更快——比较公式很难。我们想找到一种简化这些公式的办法，使得

- 不必考虑对最终时间影响不大的信息；
- 容易估计不同算法对大数输入时的运行时间；
- 容易比较哪个算法更适合某类输入。

为此发明了 O 记号——用渐近运行时间代替精确值（通常也简称*渐近复杂度*）。

**定义。** 设 $f(n)$ 是某个函数。如果存在常数 $c$ 和 $n_0$，使对所有 $n \geq n_0$ 有 $g(n) < c \cdot f(n)$，则称函数 $g(n) = O(f(n))$。

例如：

- $\frac{n}{3} = O(n)$
- $\frac{n(n-1)(n-2)}{6} = O(n^3)$
- $1 + 2 + 3 + \ldots + n = O(n^2)$
- $1^2 + 2^2 + 3^2 + \ldots + n^2 = O(n^3)$
- $\log_2{n} + 3 = O(\log n)$
- $179 = O(1)$
- $10^{100} = O(1)$

在算法分析的语境下，短语「算法运行在 $O(f(n))$ 次操作」指从某个 $n$ 开始它做不超过 $c \cdot f(n)$ 次操作。

用这种记号可以说

- 冒泡排序运行在 $O(n^2)$；
- 选择排序运行在 $O(n^2)$；
- 插入排序运行在 $O(n^2)$；
- 计数排序运行在 $O(n + m)$。

这种记号方便之处在于它简短明了，且不依赖乘以或加上常数。例如，如果算法运行在 $O(n^2)$，它可能实际运行在 $n^2$、$n^2 + 3$、$\frac{n(n-1)}{2}$，甚至 $1000 \cdot n^2 + 1$ 次操作。关键是函数行为像 $n^2$，即 $n$ 增大时它按某个二次函数增长：如果把 $n$ 增大 10 倍，程序运行时间大约增大 100 倍。

O 记号的主要优势在于，关于 `swap` 有多少操作、是否单独数赋值、比较和循环——这些讨论都消失了。无论这些问题的答案如何，它们只会把答案改变常数倍，因此算法的渐近运行时间不变。

因此前三种排序称为*平方级*——它们运行在 $O(n^2)$。计数排序可以快得多——运行在 $O(n + m)$，而如果 $m \leq n$，那就完全是线性函数 $O(n)$。
