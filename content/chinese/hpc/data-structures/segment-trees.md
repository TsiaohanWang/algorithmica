### 动态前缀和

<!--

这是一篇很长的文章，为了让它不那么长，我们将主要聚焦于它最简单的应用 -->

线段树很酷，能做的事情很多，但本文我们将聚焦于它最简单的非平凡应用——*动态前缀和问题*：

```cpp
void add(int k, int x); // 对 a[k] += x 作出反应（下标从 0 开始）
int sum(int k);         // 返回前 k 个元素的和（从 0 到 k - 1）
```

由于我们必须支持两类查询，优化问题就变成了多维的，最优解取决于查询的分布。例如，如果某类查询极其罕见，我们就只需为另一类优化，这相对容易做到：

- 如果我们只关心*更新数组*的代价，就按原样存数组，并在每次 `sum` 查询时[直接计算和](/hpc/simd/reduction)。
- 如果我们只关心*前缀和查询*的代价，就随时保前缀和就绪，并在每次更新时[从头全部重算](/hpc/algorithms/prefix)。

这两种方案都在一类查询上花 $O(1)$ 的工夫，而在另一类上花 $O(n)$。当查询频率相对接近时，我们可以在某一类查询上牺牲一点性能，来换取另一类性能的提升。线段树正是让你做到这一点，在两类查询上都达到 $O(\log n)$ 的平衡。

### 线段树结构

线段树背后的核心思想是这样的：

- 计算整个数组的和并写到某处；
- 把数组分成两半，计算两半各自的和，也把它们写到某处；
- 把这两半再各自分成两半，计算四个和的总和，也写下来；
- ……如此下去，直到递归到达长度为 1 的段。

这些计算出的子段和可以逻辑上表示为一棵二叉树——这就是我们所说的*线段树*：

![一棵线段树，高亮标出与 sum(11) 和 add(10) 查询相关的节点](../img/segtree-path.png)

线段树有一些很好的性质：

- 如果底层数组有 $n$ 个元素，线段树正好有 $(2n - 1)$ 个节点——$n$ 个叶子和 $(n - 1)$ 个内部节点——因为每个内部节点把一段一分为二，而只需要 $(n - 1)$ 个内部节点就能完整地切开原来的 $[0, n-1]$ 区间。
- 树高为 $\Theta(\log n)$：从根开始，往下一层的节点数大约翻倍，而它们所辖段的大小大约减半。
- 每个段都能被切成 $O(\log n)$ 个互不相交的段，这些段对应线段树的节点：每层最多需要两个。

当 $n$ 不是 2 的整数次幂时，并非所有层都填满——最后一层可能不完整——但这些性质的真实性不受影响。第一个性质让我们只用 $O(n)$ 内存存储树，后两个性质让我们能在 $O(\log n)$ 时间内解决问题：

- `add(k, x)` 查询可以通过把值 `x` 加到所有其段包含元素 `k` 的节点上来处理，而我们已经确认这样的节点只有 $O(\log n)$ 个。
- `sum(k)` 查询可以通过找出所有共同组成 `[0, k)` 前缀的节点、并对其中存储的值求和来回答——同样，我们也已确认这样的节点至多有 $O(\log n)$ 个。

但这仍然是理论。后面我们会看到，实现这种数据结构的方式多得惊人。

### 基于指针的实现

实现线段树最直白的方式，是把所有需要的东西都显式存在节点里：包括数组段的边界、和，以及指向其子节点的指针。

如果是在「面向对象入门」课上，我们会像这样递归地实现线段树：

```c++
struct segtree {
    int lb, rb;                         // 该节点负责的区间
    int s = 0;                          // 元素 [lb, rb) 的和
    segtree *l = nullptr, *r = nullptr; // 指向其子节点的指针

    segtree(int lb, int rb) : lb(lb), rb(rb) {
        if (lb + 1 < rb) { // 如果节点不是叶子，就创建子节点
            int m = (lb + rb) / 2;
            l = new segtree(lb, m);
            r = new segtree(m, rb);
        }
    }

    void add(int k, int x) { /* 对 a[k] += x 作出反应 */ }
    int sum(int k) { /* 计算前 k 个元素的和 */ }
};
```

如果需要在现有数组上构建它，我们就把构造函数的主体改成这样：

```c++
if (lb + 1 == rb) {
    s = a[lb]; // 该节点是叶子——它的和就是元素 a[lb]
} else {
    int t = (lb + rb) / 2;
    l = new segtree(lb, t);
    r = new segtree(t, rb);
    s = l->s + r->s; // 我们可以用刚算出的子节点和
}
```

构建时间对我们没什么值得关心的，所以为了减轻脑力负担，我们直接假设以后所有实现中数组都初始化为零。

现在，要实现 `add`，我们需要沿树下降直到到达叶节点，沿途把增量加到 `s` 字段上：

```c++
void add(int k, int x) {
    s += x;
    if (l != nullptr) { // 检查它是否为叶节点
        if (k < l->rb)
            l->add(k, x);
        else
            r->add(k, x);
    }
}
```

要计算某段上的和，我们可以检查查询是完全覆盖当前段、还是与它完全不相交——若满足就直接返回该节点的结果。如果两者都不是，就递归地把查询传给子节点，让它们自行处理：

```c++
int sum(int lq, int rq) {
    if (rb <= lq && rb <= rq) // 如果完全在查询内，返回和
        return s;
    if (rq <= lb || lq >= rb) // 如果与查询不相交，返回零
        return 0;
    return l->sum(lq, rq) + r->sum(lq, rq);
}
```

这个函数总共访问 $O(\log n)$ 个节点，因为它只在一个段与查询部分相交时才会派生子节点，而这样的段至多有 $O(\log n)$ 个。

对于*前缀和*，这些检查可以简化，因为查询的左边界始终为零：

```c++
int sum(int k) {
    if (rb <= k)
        return s;
    if (lb >= k)
        return 0;
    return l->sum(k) + r->sum(k);
}
```

既然我们有两类查询，也就有了两张图可以看：

![](../img/segtree-pointers.svg)

虽然这种面向对象的实现在软件工程实践上相当不错，但有几点使它性能上非常糟糕：

- 两种查询实现都用了[递归](/hpc/architecture/functions)——尽管 `add` 查询可以被尾调用优化。
- 两种查询实现都用了不可预测的[分支](/hpc/pipelining/branching)，使 CPU 流水线停顿。
- 节点存储了额外元数据。这个结构占 $4+4+4+8+8=28$ 字节，出于[内存对齐](/hpc/cpu-cache/alignment)原因被填充到 32 字节，而真正存整型之和其实只要 4 字节。
- 最重要的是，我们做了大量[指针追逐](/hpc/cpu-cache/latency)：为了下潜到子节点，我们必须取出指向子节点的指针，尽管我们完全可以从查询中预先推断出需要哪些段。

指针追逐比其他所有问题都严重好几个数量级——要消除它，就得去掉指针，让结构变为*隐式*。

### 隐式线段树

由于线段树是二叉树的一种，我们可以用 [Eytzinger 布局](../binary-search#eytzinger-layout)把节点存在一个大的数组里，用下标算术而不是显式指针来导航。

更正式地说，我们把节点 $1$ 定义为根，它持有整个数组 $[0, n)$ 的和。然后，对每个对应区间 $[l, r]$ 的节点 $v$，我们定义：

- 节点 $2v$ 为其左子节点，对应区间 $[l, \lfloor \frac{l+r}{2} \rfloor)$；
- 节点 $(2v+1)$ 为其右子节点，对应区间 $[\lfloor \frac{l+r}{2} \rfloor, r)$。

当 $n$ 是 2 的整数次幂时，这种布局把整棵树排布得非常紧凑：

![隐式线段树的内存布局，高亮标出同一查询路径](../img/segtree-layout.png)

然而，当 $n$ 不是 2 的幂时，布局就不再紧凑：虽然无论怎么切段，我们仍然正好有 $(2n - 1)$ 个节点，但它们不再完美映射到 $[1, 2n)$ 区间上。

例如，考虑在一个大小为 $17 = 2^4 + 1$ 的线段树里下潜到最右叶子时会发生什么：

- 从编号 $1$ 的根出发，它表示区间 $[0, 16]$，
- 到编号 $3 = 2 \times 1 + 1$ 的节点，表示区间 $[8, 16]$，
- 到编号 $7 = 2 \times 2 + 1$ 的节点，表示区间 $[12, 16]$，
- 到编号 $15 = 2 \times 7 + 1$ 的节点，表示区间 $[14, 16]$，
- 到编号 $31 = 2 \times 15 + 1$ 的节点，表示区间 $[15, 16]$，
- 最后到达编号 $63 = 2 \times 31 + 1$ 的节点，表示区间 $[16, 16]$。

所以，由于 $63 > 2 \times 17 - 1 = 33$，布局中有一些空位，但树的结构仍然相同，树高仍然是 $O(\log n)$。暂时我们可以忽略这个问题，只分配一个更大的数组来存节点——可以证明最右叶子的下标绝不会超过 $4n$，所以分配那么多单元总是够用：

```c++
int t[4 * N]; // 存放节点和
```

现在，要实现 `add`，我们创建一个类似的递归函数，但用下标算术代替指针。由于我们也不再在节点中存段的边界，需要在每次递归调用时重新计算它们并把它们作为参数传入：

```c++
void add(int k, int x, int v = 1, int l = 0, int r = N) {
    t[v] += x;
    if (l + 1 < r) {
        int m = (l + r) / 2;
        if (k < m)
            add(k, x, 2 * v, l, m);
        else
            add(k, x, 2 * v + 1, m, r);
    }
}
```

前缀和查询的实现大体相同：

```c++
int sum(int k, int v = 1, int l = 0, int r = N) {
    if (l >= k)
        return 0;
    if (r <= k)
        return t[v];
    int m = (l + r) / 2;
    return sum(k, 2 * v, l, m)
         + sum(k, 2 * v + 1, m, r);
}
```

在递归函数里来回传五个变量看起来有点笨拙，但性能收益显然值得：

![](../img/segtree-topdown.svg)

除了需要的内存少得多（这有利于装进 CPU 缓存）之外，这个实现的主要优势在于，我们现在可以利用[内存并行性](/hpc/cpu-cache/mlp)，并行地取回我们需要的节点，从而显著缩短两类查询的运行时间。

为了进一步提升性能，我们可以：

- 手工优化下标算术（例如，注意到无论怎样我们都得把 `v` 乘 `2`），
- 把除以二替换为显式的二进制移位（因为[编译器不一定总能自己做到](/hpc/compilation/contracts/#arithmetic)），
- 最重要的是，去掉[递归](/hpc/architecture/functions)，让实现完全迭代化。

由于 `add` 是尾递归且没有返回值，把它变成一个 `while` 循环很容易：

```c++
void add(int k, int x) {
    int v = 1, l = 0, r = N;
    while (l + 1 < r) {
        t[v] += x;
        v <<= 1;
        int m = (l + r) >> 1;
        if (k < m)
            r = m;
        else
            l = m, v++;
    }
    t[v] += x;
}
```

对 `sum` 查询做同样的事稍微难一点，因为它有两次递归调用。关键技巧是注意到：当我们发起这些调用时，其中一次保证会立即终止，因为 `k` 只能落在两半中的某一半里，所以我们可以简单地在下潜树之前检查这个条件：

```c++
int sum(int k) {
    int v = 1, l = 0, r = N, s = 0;
    while (true) {
        int m = (l + r) >> 1;
        v <<= 1;
        if (k >= m) {
            s += t[v++];
            if (k == m)
                break;
            l = m;
        } else {
            r = m;
        }
    }
    return s;
}
```

这并没有大幅提升更新查询的性能（因为它原本就是尾递归，编译器已经做了类似的优化），但前缀和查询的运行时间在所有问题规模上都大约减半：

![](../img/segtree-iterative.svg)

这个实现仍然有些问题：我们用了多达两倍于所需的内存，有昂贵的[分支](/hpc/pipelining/branching)，而且每次迭代都要维护和重新计算数组边界。要摆脱这些问题，我们需要稍微改变一下思路。

### 自底向上实现

让我们改变隐式线段树布局的定义。不再依赖父子关系，而是先把所有叶子节点强制编号到 $[n, 2n)$ 区间，然后递归地定义节点 $k$ 的父节点等于节点 $\lfloor \frac{k}{2} \rfloor$。

这个结构与之前大体相同：你仍然可以通过把任何节点编号除以二到达根（节点 $1$），而且每个节点仍然至多有两个子节点：$2k$ 和 $(2k + 1)$，因为任何其他值除以二都会得到不同的父节点编号。我们得到的好处是：强制让最后一层连续并从 $n$ 开始，所以我们可以用一半大小的数组：

```c++
int t[2 * N];
```

当 $n$ 是 2 的幂时，树的结构与之前完全相同，而且实现查询时我们可以利用这种自底向上的方式，从第 $k$ 个叶子节点出发（简单起见编号为 $N + k$），沿树上升直到到达根：

```c++
void add(int k, int x) {
    k += N;
    while (k != 0) {
        t[k] += x;
        k >>= 1;
    }
}
```

要计算 $[l, r)$ 子段上的和，我们可以维护指向需要添加的第一个和最后一个元素的指针，添加一个节点后分别递增/递减它们，并在它们收敛到同一个节点（即它们的最低公共祖先）后停止：

```c++
int sum(int l, int r) {
    l += N;
    r += N - 1;
    int s = 0;
    while (l <= r) {
        if ( l & 1) s += t[l++]; // l 是右子节点：添加它并移到表亲
        if (~r & 1) s += t[r--]; // r 是左子节点：添加它并移到表亲
        l >>= 1, r >>= 1;
    }
    return s;
}
```

令人惊讶的是，即使 $n$ 不是 2 的幂，两个查询也都能正确工作。要理解为什么，考虑一棵 13 个元素的线段树：

![](../img/segtree-permuted.png)

最后一层的第一个下标总是 2 的幂，但当数组大小不是 2 的整数次幂时，叶子元素的前缀部分会被绕到树的右侧。神奇的是，这一事实对我们的实现并不构成问题：

- `add` 查询仍然更新其父节点，即使其中一些父节点对应的是一段前缀加一段后缀，而不是一个连续的子段。
- `sum` 查询仍然计算出正确子段上的和，即使 `l` 位于那个被绕过去的前缀上、逻辑上「位于」`r` 的右侧——因为最终 `l` 会成为某一层的最后一个节点并被递增，突然跳到下一层的第一个元素，然后在树被绕过去的那部分上只添加正确的节点后继续正常运行（请看插图中变暗的节点）。

相比自顶向下方式，我们使用一半内存，也无需维护查询区间，这使代码更简单、因而更快：

![](../img/segtree-bottomup.svg)

运行基准测试时，我们用 `sum(l, r)` 过程计算一般的子段和，并把 `l` 固定为 `0`。要在前缀和查询上获得更高性能，我们希望避免维护 `l`，只像这样移动右边界：

```c++
int sum(int k) {
    int s = 0;
    k += N - 1;
    while (k != 0) {
        if (~k & 1) // 如果 k 是右子节点
            s += t[k--];
        k = k >> 1;
    }
    return s;
}
```

相反，这个前缀和实现只有当 $n$ 不是 2 的幂时才失效——因为 `k` 可能落在那个被绕过去的部分上，那样我们求和的范围就会几乎覆盖整个数组，而不是一个小的前缀。

要让它对任意数组大小都有效，我们可以重排叶子，使它们在树的最后两层中处于从左到右的逻辑顺序。在上面的例子里，这意味着给所有叶子下标加 $3$，然后把最后三个叶子上移一层，即减去 $13$。

在一般情况下，可以用预测（predication）在几个周期内做到：

```c++
const int last_layer = 1 << __lg(2 * N - 1);

// 计算叶子 k 的下标
int leaf(int k) {
    k += last_layer;
    k -= (k >= 2 * N) * N;
    return k;
}
```

实现查询时，我们需要做的就是调用 `leaf` 函数来得到正确的叶子下标：

```c++
void add(int k, int x) {
    k = leaf(k);
    while (k != 0) {
        t[k] += x;
        k >>= 1;
    }
}

int sum(int k) {
    k = leaf(k - 1);
    int s = 0;
    while (k != 0) {
        if (~k & 1)
            s += t[k--];
        k >>= 1;
    }
    return s;
}
```

最后一处润色：把 `s += t[k--]` 这一行替换为[预测](/hpc/pipelining/branchless)，可以让实现无分支（除了最后一处分支——我们仍然需要检查循环条件）：

```c++
int sum(int k) {
    k = leaf(k - 1);
    int s = 0;
    while (k != 0) {
        s += (~k & 1) ? t[k] : 0; // 会被替换成一条 cmov
        k = (k - 1) >> 1;
    }
    return s;
}
```

把这些优化组合起来，前缀和查询会快得多：

![](../img/segtree-branchless.svg)

注意，前缀和查询的延迟在 $2^{19}$ 而不是 $2^{20}$（L3 缓存边界）处开始上升。这是因为我们仍然存着 $2n$ 个整数，而且无论是否把 `t[k]` 加到 `s` 上，都会取回它。这两个问题我们其实都能解决。

### 树状数组

隐式结构很好：它们避免了指针追逐，允许并行访问所有相关节点，而且因为不在节点里存元数据，占用空间更小。比隐式结构更好的是*简洁*（succinct）结构：它们只需要存储结构所需的信息论意义上最少的空间，仅用 $O(1)$ 额外内存。

要让线段树变得简洁，我们需要审视节点里存的值，寻找冗余——那些可以从其他值推断出来的值——并删掉它们。一种做法是注意到：在每种前缀和实现里，我们都从未使用过右子节点里存的和——因此，对计算前缀和而言，这类节点是冗余的：

<!--

一种做法是利用如下事实：对每个节点 $v$ 及其子节点 $l$ 和 $r$，有 $s_v = s_l + s_r$，所以我们只需存这三个值中的两个，可以在「三角形」$(l, v, r)$ 中…

对任意节点 $p$，它的和 $s_p$ 等于其子节点中存的 $(s_l + s_r)$。因此，对任意这样的节点「三角形」，我们只需存 $s_p$、$s_l$、$s_r$ 中的任意两个，就可以从恒等式 $s_p = s_l + s_r$ 恢复出第三个。

-->

![](../img/segtree-succinct.png)

*树状数组*（*Fenwick tree*，也称 *binary indexed tree*——很快你就会明白为什么叫这个）是一种利用了这一考虑的线段树：它去掉所有*右*子节点，本质上在每一层删除每隔一个的节点，使节点总数与底层数组相同。

```c++
int t[N + 1]; // +1 是因为我们使用从 1 开始的下标
```

为了紧凑地存储这些段和，树状数组弃用了 Eytzinger 布局：取而代之的是，在本来会是线段树最后一层叶子的每个元素 $k$ 的位置，存下它第一个未被删除的祖先的和。例如：

- 元素 $7$ 会存下 $[0, 7]$ 区间上的和（$282$），
- 元素 $9$ 会存下 $[8, 9]$ 区间上的和（$-86$），
- 元素 $10$ 会存下 $[10, 10]$ 区间上的和（$-52$，即元素本身）。

如何比模拟沿树下降更快地算出给定元素 $k$ 的这个区间（更具体地说是左边界：右边界总是元素 $k$ 本身）？事实证明，当树的大小是 2 的幂且使用从 1 开始的下标时，有一个聪明的位技巧——只需去掉下标的最后一位最低位（least significant bit）：

- 元素 $7 + 1 = 8 = 1000_2$ 的左边界是 $0000_2 = 0$，
- 元素 $9 + 1 = 10 = 1010_2$ 的左边界是 $1000_2 = 8$，
- 元素 $10 + 1 = 11 = 1011_2$ 的左边界是 $1010_2 = 10$。

而要得到整数的最后一位置位位，可以用这个程序：

```c++
int lowbit(int x) {
    return x & -x;
}
```

这个技巧之所以成立，靠的是有符号数在二进制中如何用[补码](/hpc/arithmetic/integer)存储。当我们计算 `-x` 时，隐式地从一个大的 2 的幂中减去它：数的一些前缀位翻转，末尾的一些零后缀保持不变，而唯一保持不变的 1 位就是最后一位置位位——它将是 `x & -x` 中唯一幸存的位。例如：

```
+90 = 64 + 16 + 8 + 2 = (0)10110
-90 = 00000 - 10110   = (1)01010
    → (+90) & (-90)   = (0)00010
```

<!-- 更正式地说，树状数组被定义为数组 $t_i = \sum_{k=f(i)}^i a_k$，其中 $f$ 是某个满足 $f(i) \leq i$ 的函数。如果 $f$ 是「去掉最后一位」函数（`x -= x & -x`），那么查询和更新都只需更新 $O(\log n)$ 个不同的 $t$。 -->

我们已经确认树状数组就是一个大小为 `n` 的数组，其中每个元素 `k` 被定义为原数组中从 `k - lowbit(k) + 1` 到 `k`（含）的元素之和，现在是时候实现一些查询了。

实现前缀和查询很容易。`t[k]` 持有我们需要的和，只是缺少最前面 `k - lowbit(k)` 个元素，所以我们可以把它加到结果上，然后跳到 `k - lowbit(k)` 并继续，直到到达数组开头：

```c++
int sum(int k) {
    int s = 0;
    for (; k != 0; k -= lowbit(k))
        s += t[k];
    return s;
}
```

<!-- 在线段树里，这等价于从叶子 `k` 出发，直接跳到第一个是左子节点的祖先： -->

由于我们反复从 `k` 去掉最低置位位，而且这个程序等价于在线段树中访问同样的左子节点，每个 `sum` 查询至多触及 $O(\log n)$ 个节点：

![树状数组中一次前缀和查询的路径](../img/fenwick-sum.png)

为了略微提升 `sum` 查询的性能，我们用 `k &= k - 1` 一次性去掉最低位，它比 `k -= k & -k` 快一条指令：

```c++
int sum(int k) {
    int s = 0;
    for (; k != 0; k &= k - 1)
        s += t[k];
    return s;
}
```

与之前所有线段树实现不同，树状数组是一种更容易也更高效地把子段和计算为两个前缀和之差的的结构：

```c++
// [l, r)
int sum (int l, int r) {
    return sum(r) - sum(l);
}
```

更新查询编码起来更容易，但不太直观。我们需要把值 `x` 加到所有是叶子 `k` 的左子节点祖先的节点上。这样的节点下标 `m` 大于 `k`，但满足 `m - lowbit(m) < k`，从而让 `k` 落在它们的区间内。

所有这些下标都需要与 `k` 有一个公共前缀，然后在 `k` 为 `0` 的位置上是 `1`，再以一个零后缀结尾，这样那个 `1` 被抵消后，`m - lowbit(m)` 的结果小于 `k`。所有这些下标都可以这样迭代地生成：

```c++
void add(int k, int x) {
    for (k += 1; k <= N; k += k & -k)
        t[k] += x;
}
```

反复把最低置位位加到 `k` 上，会使它「更偶数」，并把它提升到它的下一个左子节点线段树祖先：

![树状数组中一次更新查询的路径](../img/fenwick-update.png)

现在，如果我们保留所有代码不变，即使 $n$ 不是 2 的幂它也能正确工作。此时树状数组并不等价于一棵大小为 $n$ 的线段树，而是等价于至多 $O(\log n)$ 棵大小为 2 的幂的线段树组成的*森林*——或者，如果你愿意这么想的话，等价于一棵用零填充到某个较大的 2 的幂的线段树。无论哪种情况，所有过程都能正确工作，因为它们绝不会触及 $[1, n]$ 区间之外的东西。

<!-- 有时人们处理 `sum` 查询时用 `k -= k & -k` 来迭代，这让这个实现显得格外对称。 -->

树状数组的性能与优化的自底向上线段树在更新查询上相近，在前缀和查询上略快：

![](../img/segtree-fenwick.svg)

图上有一个奇怪的现象。越过 L3 缓存边界后，性能急剧下降。这是一种[缓存组相联性](/hpc/cpu-cache/associativity)效应：最常访问的单元的下标都能被较大的 2 的幂整除，因此它们被映射到同一个缓存组，相互挤出对方，实际上缩小了缓存大小。

抵消这种效应的一种方式是像这样在布局里插入「空洞」：

```c++
inline constexpr int hole(int k) {
    return k + (k >> 10);
}

int t[hole(N) + 1];

void add(int k, int x) {
    for (k += 1; k <= N; k += k & -k)
        t[hole(k)] += x;
}

int sum(int k) {
    int res = 0;
    for (; k != 0; k &= k - 1)
        res += t[hole(k)];
    return res;
}
```

计算 `hole` 函数不在迭代之间的关键路径上，所以它不会带来明显开销，却能完全消除缓存组相联性问题，并把大数组上的延迟缩短最多 3 倍：

![](../img/segtree-fenwick-holes.svg)

树状数组很快，但它们还有一些次要问题。与[二分查找](../binary-search)类似，它们的内存访问的时间局部性不是最好的，因为不常访问的元素与最常访问的元素挤在一起。树状数组还会执行非常数次的迭代，并必须在循环末尾做检查，很可能会引起一次分支预测失败——不过也就这一次。

可能还有一些地方可以优化，但我们就在这里打住，把注意力转向一种完全不同的方法；如果你了解 [S 树](../s-tree)，大概已经猜到这要往哪去了。

### 宽线段树

核心想法是这样的：既然内存系统反正会替我们取回一整条[缓存行](/hpc/cpu-cache/cache-lines)，那就让它装满能让我们更快处理查询的信息。对线段树而言，这意味着在一个节点里存不止一个数据点。这能让我们降低树高，在沿树下行或上行时执行更少的迭代：

![](../img/segtree-wide.png)

我们将用*宽（B 叉）线段树*这个术语来指称这种改造。

要实现这种布局，我们可以用与 [S+ 树](../s-tree#implicit-b-tree-1)中类似的基于 [constexpr](/hpc/compilation/precalc) 的方法：

```c++
const int b = 4, B = (1 << b); // 缓存行大小（以整数计，而非字节）

// n 个元素数组上树的层数
constexpr int height(int n) {
    return (n <= B ? 1 : height(n / B) + 1);
}

// 第 h 层从哪里开始
constexpr int offset(int h) {
    int s = 0, n = N;
    while (h--) {
        n = (n + B - 1) / B;
        s += n * B;
    }
    return s;
}

constexpr int H = height(N);
alignas(64) int t[offset(H)]; // 存节点的数组
```

这样，我们实际上把树高缩小了大约 $\frac{\log_B n}{\log_2 n} = \log_2 B$ 倍（若 $B = 16$ 则约 $4$ 倍），但要高效地在节点内部实现操作就变得不那么平凡了。对我们的问题，有两个主要选择：

1. 在每个节点存 $B$ 个*和*（对应它的 $B$ 个子节点）。
2. 在每个节点存 $B$ 个*前缀和*（第 $i$ 个是前 $(i + 1)$ 个子节点之和）。

如果选第一种，`add` 查询与自底向上线段树大体相同，但 `sum` 查询需要在访问的每个节点里累加至多 $B$ 个标量。如果选第二种，`sum` 查询就很平凡，但 `add` 查询需要在访问的每个节点里对某个后缀加上 `x`。

无论哪种，一个操作执行 $O(\log_B n)$ 次，每次只触及每个节点里的一个标量；另一个操作则执行 $O(B \cdot \log_B n)$ 次，触及每个节点里至多 $B$ 个标量。不过，我们可以用 [SIMD](/hpc/simd) 加速较慢的那个操作。由于 SIMD 指令集里没有快速的[水平归约](/hpc/simd/reduction)，但给向量加向量很容易，我们选择第二种方案：在每个节点里存前缀和。

这让 `sum` 查询极快且极易实现：

```c++
int sum(int k) {
    int s = 0;
    for (int h = 0; h < H; h++)
        s += t[offset(h) + (k >> (h * b))];
    return s;
}
```

`add` 查询更复杂也更慢。我们需要只给节点的一个后缀加一个数，这可以通过[掩码屏蔽掉](/hpc/simd/masking)不应修改的位置来做。

我们可以预计算一张 $B \times B$ 的数组，对应 $B$ 个这样的掩码，它告诉我们：对节点内的每个位置，某个前缀和值是否需要更新：

```c++
struct Precalc {
    alignas(64) int mask[B][B];

    constexpr Precalc() : mask{} {
        for (int k = 0; k < B; k++)
            for (int i = 0; i < B; i++)
                mask[k][i] = (i > k ? -1 : 0);
    }
};

constexpr Precalc T;
```

除了这个掩码技巧，其余计算简单到只用 [GCC 向量类型](/hpc/simd/intrinsics#gcc-vector-extensions)就足以处理。处理 `add` 查询时，我们只需用这些掩码对广播后的 `x` 值做按位与来屏蔽它，然后加到节点里存的值上：

```c++
typedef int vec __attribute__ (( vector_size(32) ));

constexpr int round(int k) {
    return k & ~(B - 1); // = k / B * B
}

void add(int k, int x) {
    vec v = x + vec{};
    for (int h = 0; h < H; h++) {
        auto a = (vec*) &t[offset(h) + round(k)];
        auto m = (vec*) T.mask[k % B];
        for (int i = 0; i < B / 8; i++)
            a[i] += v & m[i];
        k >>= b;
    }
}
```

相比树状数组，这使 `sum` 查询快了 10 倍以上，`add` 查询快了最多 4 倍：

![](../img/segtree-simd.svg)

与 [S 树](../s-tree)不同，这个实现里块大小可以很容易地改变（只需改动一个字符）。可以预期，增大它时更新耗时也会上升，因为需要取回并处理更多缓存行，但 `sum` 查询耗时下降，因为树高变小了：

![](../img/segtree-simd-others.svg)

与 [S+ 树](../s-tree/#modifications-and-further-optimizations)类似，最优的内存布局可能具有非均匀的块大小，取决于问题规模和查询分布，但我们不打算探索这个想法，就在这里收手。

### 改造

我们只聚焦于 32 位整数的前缀和问题——好让这篇本已很长的文章稍微短一点，也好让与树状数组的对比更公平——但宽线段树也能用于其他常见的区间操作，虽然用 SIMD 高效地实现它们需要一些创造力。

*免责声明：* 我并未实现这些想法中的任何一个，所以其中一些可能存在致命的缺陷。

**其他数据类型**可以很容易地通过改变向量类型来支持；如果它们大小不同，还要改节点大小 $B$——这也会改变树高，从而改变两个查询的总迭代次数。

也可能是查询对更新和前缀和有不同的位数限制。例如，很常见的是只有「$\pm 1$」更新查询，且保证前缀和查询的结果始终能放进 32 位整数。如果结果能放进 8 位，我们就直接用 8 位 `char`，块大小取 $B=64$ 字节，使总树高缩小 $\frac{\log_{16} n}{\log_{64} n} = \log_{16} 64 = 1.5$ 倍，两个查询也随之成比例加快。

遗憾的是，一般情况下这行不通，但当更新增量很小时，我们仍有一种加快查询的办法：可以*缓冲*更新查询。沿用「$\pm 1$」的例子，我们可以把分支因子设为想要的 $B=64$，在每个节点里存 $B$ 个 32 位整数、$B$ 个 8 位有符号字符，以及一个从 $127$ 开始、每次更新节点时递减的 8 位计数器。然后，当我们处理节点中的查询时：

- 对于更新查询，我们给 `char` 数组加一个带掩码的 8 位正负一向量，递减计数器；如果它归零，就[把](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html#ig_expand=3037,3009,4870,6715,4845,3853,288,6570,90,7307,5993,2692,6946,6949,5456,6938,5456,1021,3007,514,518,7253,7183,3892,5135,5260,3915,4027,3873,7401,4376,4229,151,2324,2310,2324,591,4075,3011,3009,6130,4875,6385,5259,6385,6250,1395,7253,6452,7492,4669,4669,7253,1039,1029,4669,4707,7253,7242,848,879,848,7251,4275,879,874,849,833,6046,7250,4870,4872,4875,849,849,5144,4875,4787,4787,4787,3016,3018,5227,7359,7335,7392,4787,5259,5230,5230,5223,5214,6438,5229,488,483,6527,6527,6554,1829,1829,1829&techs=AVX,AVX2&text=cvtepi8_) `char` 数组里的值扩展为 32 位整数，加到整数数组上，把 `char` 数组清零，再把计数器重置回 127。
- 对于前缀和查询，我们访问同样的节点，但把 `int` 和 `char` 的值都加到结果上。

这个更新累积技巧能让我们以多用约 25% 内存为代价，把性能提升最多 1.5 倍。

在 `add` 查询里加条件分支、以及把 `char` 数组加到 `int` 数组上，都相当慢，但由于每 127 次迭代才需要做一次，在均摊意义上不花我们什么代价。`sum` 查询的处理时间会上升，但并不显著——因为它主要取决于最慢的一次读取，而不是迭代次数。

**一般区间查询**可以像树状数组那样支持：只需把区间 $[l, r)$ 分解为两个前缀和 $[0, r)$ 与 $[0, l)$ 之差。

这对加法之外的一些操作（模素数的乘法、异或等）同样成立，只要它们是*可逆的*：应当能快速把左前缀上的操作从最终结果中「抵消」掉。

**不可逆操作**也能支持，但它们仍需满足一些其他性质：

- 必须是*结合的*：$(a \circ b) \circ c = a \circ (b \circ c)$。
- 必须有*单位元*：$a \circ e = e \circ a = a$。

（如果你是个讲究的人，这种代数结构叫[幺半群](https://en.wikipedia.org/wiki/Monoid)。）

遗憾的是，当操作不可逆时，前缀和技巧行不通，所以我们必须切换到[方案一](#wide-segment-trees)，为每个段分别存下这些操作的结果。这需要对查询做一些重大改动：

- 更新查询应替换叶子处的一个标量，在叶节点处做一次[水平归约](/hpc/simd/reduction/#horizontal-summation)，然后继续向上，替换其父节点的一个标量，如此类推。
- 区间归约查询应针对左右两个边界分别计算它们路径上垂直归约后的值向量，把这两个向量合并成一个，然后水平归约它返回最终答案。注意我们仍需要用掩码把查询范围外的值替换为单位元，而且这次很可能需要一些条件移动/混合，并且要么用 $B \times B$ 的预计算掩码，要么用两个掩码分别处理查询的左右边界。

这让两个查询都慢得多——尤其是归约——但相比自底向上线段树应该仍然更快。

**最小值**是一个不错的例外：当元素的新值小于当前值时，更新查询可以稍快一些：我们可以跳过水平归约部分，直接用标量过程更新 $\log_B n$ 个节点。

当我们大多数时候都是这种更新时（例如边多于顶点的稀疏图 Dijkstra 算法就是这种情况），这会非常快。对这个问题，宽线段树可以充当高效的值域固定（fixed-universe）最小堆。

**懒惰传播**可以通过在节点里另存一个数组存放延迟操作来实现。要传播更新，我们需要自顶向下走（只需把 `for` 循环方向反过来，并用 `k >> (h * b)` 计算第 `h` 层祖先即可），[广播](/hpc/simd/moving/#broadcast)并重置当前节点父节点中存的延迟操作值，然后用 SIMD 把它应用到当前节点里存的所有值上。

一个小问题是：对某些操作，我们需要知道段的长度。例如，当需要支持一个和以及一次整体赋值时。这可以通过以下方式解决：给元素填充，使某一层上的每段大小均匀；或者预先计算段长并存进节点；或者用预测来检查有问题的节点（每层至多一个）。
