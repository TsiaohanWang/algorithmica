针对*延迟*的优化通常与针对*吞吐量*的优化很不一样：

- 在优化数据结构查询或小型一次性、带分支的算法时，你需要[查阅其指令的延迟](../tables)，在脑中构造出计算的执行图，然后尝试重新组织它，使关键路径更短。<!-- [二进制 GCD](/hpc/algorithms/gcd) 就是一个很好的例子。 -->
- 在优化热循环和大数据集算法时，你需要查阅其指令的吞吐量，统计每次迭代中每条指令的使用次数，确定哪一条是瓶颈，然后尝试重构循环，让它被用得更少。

最后这条建议只对*数据并行（data-parallel*）的循环有效，即每次迭代与前一次完全独立。当相邻迭代之间存在某种相互依赖时，下一次迭代可能要等待上一次完成，从而可能因[数据冒险](../hazards)导致流水线停顿。

### 例子

举个简单的例子：看看数组求和是如何计算的：

```c++
int s = 0;

for (int i = 0; i < n; i++)
    s += a[i];
```

我们先暂时假设编译器不会[向量化](/hpc/simd)这个循环，[内存带宽](/hpc/cpu-cache/bandwidth)也不是问题，并且循环[已经展开](/hpc/architecture/loops)，这样我们就不必为维护循环变量付出额外代价。在这种情况下，计算变得非常简单：

```c++
int s = 0;
s += a[0];
s += a[1];
s += a[2];
s += a[3];
// ...
```

我们能算多快？恰好每元素一个周期——因为每次迭代都需要一个周期来把另一个值 `add` 到 `s` 上。内存读取的延迟无关紧要，因为 CPU 可以提前开始它。

但我们还能做得更快。在我的 CPU（Zen 2）上，`add` 的*吞吐量*[^throughput]是 2，也就是说理论上每周期可以执行两条。但现在这还做不到：当 `s` 正在累加第 $i$ 个元素时，至少一个周期内它不能被用于累加第 $(i+1)$ 个元素。

[^throughput]: 寄存器-寄存器 `add` 的吞吐量是 4，但由于我们要从内存中读取它的第二个操作数，它受内存 `mov` 的吞吐量所限，而后者在 Zen 2 上为 2。

解决办法是使用*两个*累加器，把奇数元素和偶数元素分开累加：

```c++
int s0 = 0, s1 = 0;
s0 += a[0];
s1 += a[1];
s0 += a[2];
s1 += a[3];
// ...
int s = s0 + s1;
```

现在我们的超标量 CPU 可以同时执行这两个“线程”，我们的计算不再有任何限制吞吐量的关键路径。

### 一般情形

如果一条指令的延迟为 $x$、吞吐量为 $y$，那么你需要使用 $x \cdot y$ 个累加器才能把它喂饱。这也意味着你需要 $x \cdot y$ 个逻辑寄存器来存放它们的值——这是 CPU 设计中的一个重要考量，它限制了高延迟指令可用的执行单元数量上限。

这种技术主要与 [SIMD](/hpc/simd) 一起使用，而不是用于标量代码。你可以[推广](/hpc/simd/reduction)上面的代码，比编译器更快地计算求和及其他归约。

一般来说，在优化循环时，你通常只有一两个*执行端口*想要充分利用，并围绕它们设计循环的其余部分。由于不同指令可能使用不同的端口集合，哪个端口会被过度使用并不总是显而易见。在这种情况下，[机器码分析器](/hpc/profiling/mca)对找出小型汇编循环的瓶颈会非常有帮助。
