当程序员听到“并行（parallelism）”这个词时，他们大多想到的是“多核并行（multi-core parallelism）”，即显式地把一次计算拆分成若干半独立的“线程（thread）”，让它们协同解决同一个问题。

这类并行主要着眼于降低“延迟（latency）”和实现“可扩展性（scalability）”，而不是提升“效率（efficiency）”。并行算法可以解决规模大十倍的同一类问题，但代价是至少多消耗十倍的计算资源。虽然并行硬件正变得[前所未有地普及](/hpc/complexity/hardware)，并行算法设计也日益成为一个重要的领域，但眼下我们只考虑单个 CPU 核心。

不过，在 CPU 核心内部还存在着其他类型的并行，你可以“免费”使用它们。

### 指令流水线

要执行*任何*一条指令，处理器都得先做大量的准备工作，包括：

- 从内存中**取指（fetch）**一段机器码，
- **译码（decode）**并将其拆分成指令，
- **执行（execute）**这些指令，其中可能包含一些**内存**操作，以及
- 把结果**写回**寄存器。

这一整串操作是*漫长*的。哪怕只是把两个寄存器中的值相加这样的 `add` 指令，也要耗费多达 15–20 个 CPU 周期。为了隐藏这段延迟，现代 CPU 采用*流水线（pipelining）*：一条指令通过第一级流水段之后，处理器立刻开始处理下一条，无需等待前一条完全执行完毕。

![](img/pipeline.png)

流水线并不能降低*实际*延迟，但在功能上让延迟看起来似乎只由执行和访存两个阶段构成。你仍然要为这 15–20 个周期买单，只不过只需在确定将要执行的指令序列之后付一次。

正因如此，硬件厂商更愿意用*每指令周期数*（cycles per instruction，CPI），而不是诸如“平均指令延迟”之类的指标，作为 CPU 设计的主要性能指标。倘若我们只考虑*有用*的指令，它对算法设计同样是一个[相当不错的指标](/hpc/profiling/benchmarking)。

完美流水线化的处理器的 CPI 应当趋近于 1，不过实际上它还能更低：把流水线的每一级“加宽”，即复制一份，使得同一时刻能处理多条指令。由于缓存和大部分 ALU 可以共享，这样做比增加一个完全独立的核心更划算。这种每周期能执行超过一条指令的架构称为*超标量（superscalar）*，大多数现代 CPU 都是超标量的。

只有当指令流中包含可以分开处理的、逻辑上相互独立的操作组时，你才能从超标量处理中获益。指令并不总是以最方便的顺序到来，因此现代 CPU 会在可行时*乱序（out of order）*执行它们，以提高整体利用率、减少流水线停顿。这一魔法背后的原理属于更深入的讨论话题<!--[更深入的讨论](scheduling)-->，眼下你只需要假设：CPU 维护着一个面向未来某段距离内待处理指令的缓冲区，一旦某个操作数的值被算出来、且有执行单元空闲，就立刻执行该指令。

### 一个教育行业的类比

想一想我们的教育体系是如何运作的：

1. 课程是同时对整组学生讲授，而不是逐个学生单独授课，因为把同样的内容一次性广播给所有人更高效。
2. 一届学生会被分到不同的班级，由不同的老师负责；作业和其他课程资料在班级之间共享。
3. 每年同样的课程都会教给新一届学生，这样老师们就能一直有事可做。

这些创新极大地提高了整个系统的*吞吐量（throughput）*，尽管*延迟*（某个学生毕业所需的时间）保持不变（甚至可能略增，因为一对一的辅导更有效）。

你可以在现代 CPU 中找到许多与之对应的类比：

1. CPU 使用 [SIMD 并行](/hpc/simd)对一块不同的数据点（由 16、32 或 64 字节组成）执行相同操作。
2. 存在多个执行单元，它们可以同时处理这些指令，同时共享 CPU 的其他设施（通常有 2–4 个执行单元）。
3. 指令以流水线方式处理（节省的周期数大约相当于从幼儿园到博士之间的年数）。

除此之外，还有几个方面也对得上：

- 执行路径会随着时间推移而越来越分化，需要不同的执行单元。
- 有些指令可能由于各种原因被停顿。
- 有些指令甚至会被推测执行（提前执行），但之后又被丢弃。
- 有些指令会被拆分成若干独立的微操作，各自独立推进。

为流水线和超标量处理器编程有其自身的挑战，这正是本章将要讨论的内容。
