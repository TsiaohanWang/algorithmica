当 CPU 遇到条件跳转或[任何其他类型的分支](/hpc/architecture/indirect)时，它并不会傻等到条件计算完毕——而是立刻开始*推测执行*看似更可能被采纳的那个分支。在执行过程中，CPU 会统计每条指令上分支被采纳的情况，经过一段时间后，它就能通过识别常见模式来预测分支。

正因如此，分支真正的“代价”在很大程度上取决于 CPU 对它的预测能力。如果它是一场彻头彻尾的 50/50 抛硬币赌局，你就得承受[控制冒险](../hazards)，丢弃整条流水线，再花上 15–20 个周期重新建立起来。而如果这个分支总是被采纳或总是不被采纳，你几乎不用付出任何代价，只需检查一下条件。

## 一个实验

作为案例研究，我们创建一个包含 0 到 99（含）之间随机整数的数组：

```c++
for (int i = 0; i < N; i++)
    a[i] = rand() % 100;
```

然后我们写一个循环，把所有小于 50 的元素累加起来：

```c++
volatile int s;

for (int i = 0; i < N; i++)
    if (a[i] < 50)
        s += a[i];
```

我们令 $N = 10^6$，并把这个循环反复运行很多次，以免[冷缓存](/hpc/cpu-cache/bandwidth)效应干扰我们的结果。我们把累加变量标记为 `volatile`，这样编译器就不会对循环做向量化、交错迭代，或以其他任何方式“作弊”。

在 Clang 上，这段代码生成的汇编大致如下：

```nasm
    mov  rcx, -4000000
    jmp  body
counter:
    add  rcx, 4
    jz   finished   ; "jump if rcx became zero"
body:
    mov  edx, dword ptr [rcx + a + 4000000]
    cmp  edx, 49
    jg   counter
    add  dword ptr [rsp + 12], edx
    jmp  counter
```

我们的目的是模拟一个完全无法预测的分支，而且成功做到了：这段代码每个元素大约花费 14 个 CPU 周期。为了粗略估算其理论值，我们可以假设分支在 `<` 和 `>=` 之间交替出现，流水线每隔一次迭代就预测失败一次。于是每两次迭代：

- 我们丢弃整条流水线，它在 Zen 2 上有 19 级深（即它有 19 个流水段，每段各占一个周期）。
- 我们需要一次内存读取和一次比较，约花费 5 个周期。偶数和奇数迭代的条件可以同时检查，所以我们假设每 2 次迭代只需付一次这个代价。
- 在 `<` 分支的情况下，我们还需要约 4 个周期把 `a[i]` 加到 volatile（存储在内存中的）变量 `s` 上。

因此平均下来，每个元素需要花费 $(4 + 5 + 19) / 2 = 14$ 个周期，与我们的实测结果一致。

### 分支预测

我们可以把硬编码的 `50` 换成一个可调参数 `P`，它实际上决定了 `<` 分支的概率：

```c++
for (int i = 0; i < N; i++)
    if (a[i] < P)
        s += a[i];
```

现在，如果我们对不同的 `P` 值做基准测试，会得到一张很有意思的图：

![](../img/probabilities.svg)

不出所料，峰值出现在 50–55% 处：分支预测失败是这里最昂贵的东西。这张图是不对称的：只检查那些永不被满足的条件（`P = 0`）仅需约 1 个周期，而分支总是被采纳（`P = 100`）时求和需要约 7 个周期。

这张图并不是单峰的：在约 85–90% 处还有另一个局部最小值。在那里我们每个元素花费约 6.15 个周期，比始终采纳该分支时快约 10–15%，这还没算我们需要的加法更少。此时分支预测失败不再影响性能，因为当预测失败发生时，被丢弃的不是整个指令缓冲区，而只有那些被推测调度的操作。本质上，这个 10–15% 的预测失败率就是平衡点：在这个点上，我们往前看得足够远，不至于停顿，同时又能因为采纳更廉价的 `>=` 分支而节省 10–15%。

注意，检查一个从不或几乎从不发生的情况几乎不花任何代价。这正是程序员如此大量使用运行时异常和基本情况检查的原因：如果它们确实很少发生，就真的不花什么钱。

### 模式识别

在我们的例子中，高效分支预测所需要的一切不过是一个硬件统计计数器。如果历史上分支 A 比分支 B 更常被采纳，那么推测执行分支 A 就是合理的。但现代 CPU 上的分支预测器远比这先进，它们能识别复杂得多的模式。

我们把 `P` 重新固定为 50，然后在主求和循环之前先把数组排序：

```c++
for (int i = 0; i < N; i++)
    a[i] = rand() % 100;

std::sort(a, a + n);
```

我们处理的仍是同样的元素，只是顺序不同；现在它不再需要 14 个周期，而只比 4 个周期多一点——这恰好是纯 `<` 分支与纯 `>=` 分支代价的平均值。

分支预测器能识别的模式远不止“总是左、然后总是右”或“左-右-左-右”。如果我们只是把数组规模 $N$ 减小到 1000（不排序），分支预测器会把整条比较序列记下来，基准测试又会测得约 4 个周期——实际上甚至比排序数组的情况还略少一点，因为在前一种情况下，分支预测器需要花些时间在“总是是”和“总是否”两种状态之间来回切换。

### 向编译器提示分支可能性

如果你预先知道哪个分支更可能被采纳，把这一信息[传给编译器](/hpc/compilation/situational)或许是有益的：

```c++
for (int i = 0; i < N; i++)
    if (a[i] < P) [[likely]]
        s += a[i];
```

当 `P = 75` 时，它测得每元素约 7.3 个周期，而没有这个提示的原始版本则需要约 8.3 个周期。

这个提示既不会消除分支，也不会向分支预测器传递任何信息，但它会改变[机器码布局](/hpc/architecture/layout)，让 CPU 前端能以略快的速度处理更可能被采纳的那个分支（不过通常不会超过一个周期）。

这种优化只有在你于编译阶段之前就知道哪个分支更可能被采纳时才有效。当分支从根本上就无法预测时，我们可以尝试用*谓词化（predication）*把它彻底消除——这是一项极其重要的技术，我们将在[下一节](../branchless)中探讨。
