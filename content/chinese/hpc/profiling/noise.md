常常会出现这样的情况：两个库算法实现各自维护一套基准测试代码，各自宣称比对方更快。这让所有相关的人都感到困惑，尤其是那些不得不在两者之间做选择的用户。

这类情况通常并非作者弄虚作假所致；他们只是对「更快」有不同的定义。而事实上，定义并使用单一的性能指标往往本身就很有问题。

### 测量正确的东西

有许多东西会给基准测试带来偏差。

**不同的数据集。** 很多算法的性能或多或少依赖于数据集的分布。为了定义例如最快的排序、最短路或二分查找算法，你必须固定算法运行时所用的数据集。

这有时甚至适用于处理单个输入的算法。例如，给 GCD 实现喂顺序连续的整数并不是好主意，因为那会让分支变得非常可预测：

```c++
// 不要这样做
int checksum = 0;

for (int a = 0; a < 1000; a++)
    for (int b = 0; b < 1000; b++)
        checksum ^= gcd(a, b);
```

然而，如果我们随机采样这些相同的数，分支预测就会变得困难得多，基准测试耗时也会更长——尽管处理的是同样的输入，只是顺序变了：

```c++
int a[1000], b[1000];

for (int i = 0; i < 1000; i++)
    a[i] = rand() % 1000, b[i] = rand() % 1000;

int checksum = 0;

for (int t = 0; t < 1000; t++)
    for (int i = 0; i < 1000; i++)
        checksum += gcd(a[i], b[i]);
```


尽管对大多数情况而言最合理的选择就是均匀随机采样，但许多真实应用的数据分布远非均匀，所以你无法只挑一种。一般而言，一个好的基准测试应该与应用相关，并且尽量使用最能代表你真实使用场景的数据集。

**多目标。** 有些算法设计问题不止一个关键目标。例如，哈希表除了高度依赖键的分布外，还需要仔细权衡：

- 内存占用，
- 添加查询的延迟，
- 正向成员查询的延迟，
- 负向成员查询的延迟。

选择哈希表实现的唯一方法，就是把多个变体都放进应用里去试。

**延迟 vs 吞吐量。** 另一个人们常常忽略的方面是：即使对单个查询，执行时间的定义方式也不止一种。

当你写出这样的代码：

```c++
for (int i = 0; i < N; i++)
    q[i] = rand();

int checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);
```

然后给整个过程计时并除以迭代次数，你实际测量的是该查询的*吞吐量*——单位时间内能处理多少次操作。由于指令的交错，这通常小于单独处理一次操作实际所需的时间。

要测量真正的*延迟*，你需要在各次调用之间引入依赖：

```c++
for (int i = 0; i < N; i++)
    checksum ^= lower_bound(checksum ^ q[i]);
```

这在那些可能出现流水线停顿的算法里通常差异最大，例如在比较有分支与无分支算法时。

**冷缓存。** 另一个偏差来源是*冷缓存效应*：初次读取内存时耗时更长，因为所需数据还没有进入缓存。

解决办法是在开始测量之前先做一次*预热运行*：

```c++
// 预热运行

volatile checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);


// 正式运行

clock_t start = clock();
checksum = 0;

for (int i = 0; i < N; i++)
    checksum ^= lower_bound(q[i]);
```

如果校验不只是算个某种校验和那么简单，把预热运行与答案验证结合起来有时也很方便。

**过度优化。** 有时候基准测试完全出错，是因为编译器把被测试的代码整个优化掉了。要防止编译器偷工减料，你需要加入校验和，要么把它打印到某处，要么加上 `volatile` 限定符——后者还能防止循环迭代的任何交错。

对于只写数据的算法，你可以用 `__sync_synchronize()` 内建函数加上内存屏障，防止编译器累积更新。

### 降低噪声

我们描述过的这些问题会在测量中造成*偏差*：它们始终如一地偏向某个算法。基准测试还有另外一类可能的问题，会导致不可预测的偏移或纯粹的随机噪声，从而增大*方差*。

这类问题由副作用和某种外部噪声引起，主要是「嘈杂邻居」和 CPU 频率缩放：

- 如果你测试的是计算密集型算法，用 `perf stat` 以周期为单位衡量其性能：这样它就与时钟频率无关，而频率波动通常是噪声的主要来源。
- 否则，把核心频率设为期望值，并确保没有东西干扰它。在 Linux 上可以用 `cpupower` 来做（例如 `sudo cpupower frequency-set -g powersave` 设为最低，或 `sudo cpupower frequency-set -g ondemand` 启用睿频）。我使用一个[方便的 GNOME shell 扩展](https://extensions.gnome.org/extension/1082/cpufreq/)，它有一个单独的按钮来做这件事。
- 如果适用，关闭超线程并把任务绑定到特定核心。确保系统上没有其他任务在运行，关闭网络，尽量不要碰鼠标。

你无法完全消除噪声和偏差。甚至程序的名字都能影响它的速度：可执行文件的名字会进入环境变量，环境变量会出现在调用栈上，于是名字的长度会影响栈对齐，进而可能导致数据访问因跨越缓存行或内存页边界而变慢。

在指导优化时，尤其是在向别人报告结果时，把噪声考虑在内非常重要。除非你期待的是 2 倍左右的提升，否则应把所有微基准测试都当作 A/B 测试来对待。

当你在笔记本上让程序运行不到一秒时，±5% 的性能波动是完全正常的。所以，如果你要在「回退」还是「保留」某个潜在的 +1% 改进之间做决定，就跑到达到统计显著性为止——这可以通过计算方差和 p 值来判断。
