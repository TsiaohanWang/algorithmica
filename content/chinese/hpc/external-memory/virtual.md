早期的操作系统允许每个进程自由读取和修改它们想读写的任何内存区域，包括分配给其他进程的区域。这虽然保持了简单性，但也带来了一些问题：

- 如果其中一个进程有 bug 或者干脆是恶意的怎么办？我们如何防止它修改分配给其他进程的内存，同时又保留通过内存进行进程间通信的可能？
- 我们如何处理内存碎片？假设我们有 4MB 内存：进程 A 为自己分配了前 1MB，然后进程 B 占用了接下来的 2MB，接着 A 终止并释放了它的内存，然后进程 C 来了，请求一个连续的 2MB 区域——却得不到，因为我们只有两个分开的 1MB 碎片。重启进程 B，或者以某种方式停止它并把它的所有数据和指针移动 1MB，似乎都不是什么好办法。
- 我们如何访问非 RAM 的内存类型？如何插入一个闪存盘并读取其中的某个文件？

对某些专用计算机系统（如 GPU）来说，这些问题没那么关键——它们通常一次只解决一个任务，并且对计算有完全的控制权——但对现代多任务操作系统来说，这些问题绝对至关重要；而它们用一种称为*虚拟内存*的技术解决了所有这些问题。

### 内存分页

虚拟内存让每个进程觉得自己完全控制着一块连续的内存区域，而这块区域实际上可能映射到物理内存的多个更小的块上——这些物理内存既包括主内存（RAM），也包括外部存储（HDD、SSD）。

![](../img/virtual-memory.jpg)

为实现这一点，内存地址空间被划分为*页*（通常大小为 4KB），页是程序可以向操作系统请求的基本内存单位。内存系统维护一种特殊的硬件数据结构，称为*页表*，其中包含虚拟页地址到物理页地址的映射。当一个进程用它的虚拟内存地址访问数据时，内存系统计算它所在的页号（如果页大小是 $4096=2^{12}$，就把它右移 $12$ 位），在页表中查找它的物理地址，然后把读请求或写请求转发到数据实际存储的位置。

由于每次内存请求都需要进行地址转换，而内存页的数量本身可能很大（例如 16G RAM / 4K 页大小 = 4M 个页），地址转换本身就是一个难题。加速它的方法之一是使用页表专用的特殊缓存，称为 *TLB*（快表，translation lookaside buffer）；另一种方法是[增大页面大小](/hpc/cpu-cache/paging)，这样内存页的总数就会减少，代价是粒度变粗。

### 映射外部存储

虚拟内存机制还让我们可以相当透明地使用外部存储类型。现代操作系统支持[内存映射](https://en.wikipedia.org/wiki/Mmap)，它让你打开一个文件，然后像使用主内存一样使用它的内容：

```c++
// open a file containing 1024 random integers for reading and writing
int fd = open("input.bin", O_RDWR);
// map it into memory      size  allow reads and writes  write changes back to the file
int* data = (int*) mmap(0, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
// sort it like if it was a normal integer array
std::sort(data, data + 1024);
// changes are eventually propagated to the file
```

这里我们映射了一个 4K 的文件，它恰好可以完整放入一个内存页；但当打开更大的文件时，读取会在我们请求某个页时惰性地进行，写入则会被缓冲，并在操作系统决定时（通常是程序终止或系统 RAM 耗尽时）提交到文件系统。

与它运行原理相同、但意图相反的技术是*交换文件（swap file*）：当真实 RAM 不足时，它让操作系统自动把 SSD 或 HDD 的一部分用作主内存的扩展。这使内存耗尽时的系统只是经历严重的变慢，而不是崩溃。

主内存与外部存储的这种无缝整合，本质上把 RAM 变成了外部存储的「L4 缓存」——从算法设计的角度看，这是一种很方便的思考方式。
