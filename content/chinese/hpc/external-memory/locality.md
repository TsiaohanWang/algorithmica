要精确评估一个算法在内存操作方面的性能，我们需要考虑缓存系统的多个特性：缓存层的数量、每一层的[内存大小与块大小](../hierarchy)、每一层用于缓存淘汰的精确[策略](../policies)，有时甚至还包括[内存分页](../virtual)机制的细节。

在设计算法的早期阶段，把所有这些细枝末节抽象掉大有帮助。与其计算理论上的缓存命中率，不如用更定性的方式来思考缓存性能，这通常更有意义。

在本文中，我们继续为外部存储模型设计算法，并解决当缓存系统的某些细节未知时如何评估 I/O 性能的问题。

在这一背景下，我们可以主要从两个方面来讨论缓存复用的程度：

- *时间局部性*指在相对较短的时间段内重复访问同一数据，使得这些数据在两次请求之间很可能仍留在缓存中。
- *空间局部性*指使用内存位置彼此接近的元素，使得它们很可能在同一次内存块读取中被一并取回。

换句话说，时间局部性指的是同一个内存位置很可能很快又被请求；空间局部性指的是紧接着很可能请求附近的位置。

在本节中，我们将做一些案例研究，展示这些高层概念如何帮助进行实际优化。

### 深度优先与广度优先

考虑一种分治算法，例如归并排序。实现它有两种方式：

- 我们可以像通常实现的那样采用递归方式，即「深度优先」：先排序左半部分，再排序右半部分，然后合并结果。
- 我们也可以采用迭代方式，即「广度优先」：先做最底部的「层」，遍历整个数据集，把奇数元素与偶数元素两两比较合并，然后把前两个元素与后两个元素合并、再后两个元素与再后两个元素合并，依此类推。

第二种方式看起来更繁琐，但应该更快——因为递归总是很慢，对吧？

一般来说，递归[确实很慢](/hpc/architecture/functions)，但对这个算法以及许多类似的分治算法来说，情况并非如此。虽然迭代方式具有只做顺序 I/O 的优势，但递归方式的时间局部性好得多：当一个片段完全装进缓存后，它会在递归的所有更底层阶段一直留在缓存中，从而在后续获得更好的访问时间。

事实上，我们只需要把数组分割 $O(\log \frac{N}{M})$ 次就能达到这一状态，因此总共只需要读取 $O(\frac{N}{B} \log \frac{N}{M})$ 个块；而在迭代方式中，无论怎样，整个数组都会被从头读取 $O(\log N)$ 次。这带来了 $O(\frac{\log N}{\log N - \log M})$ 的加速比，最高可达一个数量级。

在实践中，递归仍然带有一些开销，因此使用混合算法是合理的：不必一路递归到基本情况，而是在递归的较底层切换到迭代代码。

### 动态规划

类似的推理可以应用于动态规划算法的实现，但会得出相反的结论。考虑经典的*背包问题*：给定 $N$ 个物品，每个物品有正整数花费 $c_i$，选出总花费不超过给定常数 $W$ 的、总花费最大的物品子集。

解决它的方法是引入*状态* $f[n, w]$，它表示只使用前 $n$ 个物品时，总花费不超过 $w$ 所能达到的最大值。如果我们考虑是否选取第 $n$ 个物品，并利用动态规划的先前状态做出最优决策，那么每个条目都可以在 $O(1)$ 时间内计算出来。

Python 有一个方便的 `lru_cache` 装饰器，可以用来实现带记忆化的递归：

```python
@lru_cache
def f(n, w):
    # check if we have no items to choose
    if n == 0:
        return 0
    
    # check if we can't pick the last item (note zero-based indexing)
    if c[n - 1] > w:
        return f(n - 1, w)
    
    # otherwise, we can either pick the last item or not
    return max(f(n - 1, w), c[n - 1] + f(n - 1, w - c[n - 1]))
```

计算 $f[N, W]$ 时，递归最多可能访问 $O(N \cdot W)$ 个不同的状态，这在渐近意义上是高效的，但实际中相当慢。即使消除了 Python 递归的开销以及 LRU 缓存工作所需的全部[哈希表查询](../policies/#implementing-caching)，它仍然会很慢，因为它在执行的大部分时间里都在做随机 I/O。

我们不妨换一种做法：为动态规划创建一个二维数组，用下面这样漂亮的嵌套循环代替递归：

```cpp
int f[N + 1][W + 1] = {0}; // this zero-fills the array

for (int n = 1; n <= N; n++)
    for (int w = 0; w <= W; w++)
        f[n][w] = c[n - 1] > w ?
                  f[n - 1][w] :
                  max(f[n - 1][k], c[n - 1] + f[n - 1][w - c[n - 1]]);
```

注意，我们只用动态规划的前一层来计算下一层。这意味着，如果我们能把一层放进缓存，就只需要在外部存储器中写入 $O(\frac{N \cdot W}{B})$ 个块。

此外，如果我们只需要答案，实际上不必存储整个二维数组，只需保留最后一层。这样，通过维护一个大小为 $W$ 的数组，我们只需要 $O(W)$ 内存。为简化代码，我们可以稍微修改动态规划，让它存储一个布尔值：能否用已考虑过的物品凑出恰好为 $w$ 的总和。这个动态规划计算起来甚至更快：

```cpp
bool f[W + 1] = {0};
f[0] = 1;
for (int n = 0; n < N; n++)
    for (int x = W - c[n]; x >= 0; x--)
        f[x + c[n]] |= f[x];
```

顺带一提，由于它现在只使用简单的位运算，还可以用位集（bitset）进一步优化：

```cpp
std::bitset<W + 1> b;
b[0] = 1;
for (int n = 0; n < N; n++)
    b |= b << c[n];
```

令人惊讶的是，这里仍有改进空间，我们稍后会回到这个问题。

### 稀疏表

*稀疏表*是一种*静态*数据结构，常用于解决*静态 RMQ* 问题，并推广到计算任何类似的*幂等区间归约*。它可以形式化地定义为大小为 $\log n \times n$ 的二维数组：

$$
t[k][i] = \min \{ a_i, a_{i+1}, \ldots, a_{i+2^k-1} \}
$$

简单来说：我们存储每个长度为 2 的幂的区间上的最小值。

这种数组可以在常数时间内计算任意区间上的最小值，因为对每个区间，我们总能找到两个大小相同（都是 2 的幂）、可能重叠的区间，它们的并集恰好覆盖整个区间。

![](../img/sparse-table.png)

这意味着我们只需取这两个预计算最小值中较小者作为答案：

```cpp
int rmq(int l, int r) { // half-interval [l; r)
    int t = __lg(r - l);
    return min(mn[t][l], mn[t][r - (1 << t)]);
}
```

`__lg` 函数是 GCC 提供的一个内建函数，它计算一个数的二进制对数并向下取整。它内部使用 `clz`（"count leading zeros"，统计前导零个数）指令，并用 32 减去这个数（对于 32 位整数而言），因此只需几个周期。

我在这篇文章中提起它的原因是，构建它有很多种不同方式，它们在内存操作方面的效率各不相同。一般来说，稀疏表可以按动态规划的方式在 $O(n \log n)$ 时间内构建：按 $i$ 或 $k$ 递增的顺序迭代，并应用下面的恒等式：

$$
t[k][i] = \min(t[k-1][i], t[k-1][i+2^{k-1}])
$$

现在有两个设计选择：是把对数长度 $k$ 作为第一维还是第二维，以及先迭代 $k$ 再迭代 $i$ 还是反过来。这意味着构建它有 $2×2=4$ 种方式，下面是最优的一种：

```cpp
int mn[logn][maxn];

memcpy(mn[0], a, sizeof a);

for (int l = 0; l < logn - 1; l++)
    for (int i = 0; i + (2 << l) <= n; i++)
        mn[l + 1][i] = min(mn[l][i], mn[l][i + (1 << l)]);
```

这是内存布局与迭代顺序的唯一组合，能够产生漂亮、线性遍历、速度大约快 3 倍的代码。作为练习，请考虑其他三种变体，思考它们*为什么*更慢。

### 数组结构体（AoS）与结构体数组（SoA）

假设你想实现一棵二叉树，并把它的字段分别存储在不同的数组中，就像这样：

```cpp
int left_child[maxn], right_child[maxn], key[maxn], size[maxn];
```

这种把每个字段分开存储的内存布局称为*结构体数组*（SoA）。在大多数情况下，实现树操作时，你会访问一个节点，随后很快访问它的全部或大部分内部数据。如果这些字段分开存储，就意味着它们位于不同的内存块中。如果所请求的某些字段恰好已被缓存、而另一些没有，你仍然要等待最慢的那个字段被取回。

相反，如果改用*数组结构体*（AoS）存储，块读取次数大约会减少到原来的 1/4，因为一个节点的全部数据都存储在同一个块中，可以一次性取回：

```cpp
struct Node {
    int left_child, right_child, key, size;
};

Node t[maxn];
```

对于数据结构来说，通常更倾向于 AoS 布局，但 SoA 仍有其用武之地：虽然它在查找方面表现较差，但在线性扫描方面要好得多。

这种设计上的差异在数据处理应用中很重要。例如，数据库可以是*行式*或*列式*（也称作 *columnar*）存储：

- *行式*存储格式用于需要在大型数据集中搜索有限数量的对象，并且/或者需要取出它们的全部或大部分字段的场景。例如：PostgreSQL、MongoDB。
- *列式*存储格式用于大数据处理和分析，在这些场景中你反正需要扫描全部数据来计算某些统计量。例如：ClickHouse、Hbase。

列式格式还有一个额外优势：由于不同字段存储在不同的外部存储区域，你可以只读取需要的字段。
