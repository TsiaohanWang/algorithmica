如果你是按顺序从头读这一章，你可能会疑惑：为什么我在讲完浮点运算之后才介绍整数运算？它难道不是应该更简单吗？

确实：朴素的整数表示更简单。但反直觉的是，这种简单性反而让运算有了更多用其他运算来表达的可能。如果说浮点表示笨重到大多数运算都由硬件实现，那么高效地操作整数则需要对指令集进行更具创造性的运用。

## 二进制格式

*无符号整数*就是用二进制书写的自然数：

$$
\begin{aligned}
   5_{10}   &= 101_2 = 4 + 1
\\ 42_{10}  &= 101010_2 = 32 + 8 + 2
\\ 256_{10} &= 100000000_2 = 2^8
\end{aligned}
$$

当运算结果无法装进字长时（例如，对 32 位无符号整数来说结果大于等于 $2^{32}$），它就会*溢出（overflow）*，只留下结果的最低 32 位。类似地，如果结果是负值，它会通过加上 $2^{32}$ 而*下溢（underflow）*，从而始终保持在 $[0, 2^{32})$ 范围内。

这等价于对所有运算取模 2 的幂：

$$
\begin{aligned}
    256                 &\equiv 0 \pmod {2^8}
\\  2021                &\equiv 229 \pmod {2^8}
\\  -42 \equiv 256 - 42 &\equiv 214 \pmod {2^8}
\end{aligned}
$$

无论哪种情况，它都会置起一个你可以检查的特殊标志；不过通常当人们明确使用无符号整数时，他们期待的正是这种行为。

### 有符号整数

*有符号整数*通过把最高位专门用来表示数的符号来支持存储负值，方式与浮点数类似。这使可表示的非负数范围减半：32 位整数现在最大只能是 $(2^{31}-1)$ 而不是 $(2^{32}-1)$。但负值的编码与浮点数并不完全相同。

计算机工程师甚至比程序员还要懒——这不仅是出于追求简化的本能，也是为了节省晶体管空间。这可以通过复用你为其他运算已有的电路来实现，这正是他们设计有符号整数格式时的目标：

- 对于 $n$ 位有符号整数类型，$[0, 2^{n-1})$ 范围内所有数的编码与其无符号二进制表示相同。
- $[-2^{n-1}, 0)$ 范围内的所有数紧跟在“正数”范围之后顺序编码——即从编码为 $(2^{n-1})$ 的 $(-2^{n - 1})$ 开始，到编码为 $(2^n - 1)$ 的 $(-1)$ 结束。

一种理解方式是：所有负数都像是从 $2^n$ 中减去它们后得到的编码——这种操作被称为*补码（two's complement）*：

$$
\begin{aligned}
-x &= 2^{32} - x
\\ &= \bar{x} + 1
\end{aligned}
$$

这里 $\bar{x}$ 表示按位取反，也可以看作是从 $(2^n - 1)$ 中减去 $x$。

作为练习，这里列举一些关于有符号整数的事实：

- 所有正数和零的编码与它们的二进制记号相同。
- 所有负数最高位都为 1。
- 负数的数量比正数多（恰好多一个——因为还有零）。
- 对于 `int`，如果给 $(2^{31}-1)$ 加上 $1$，结果将是 $-2^{31}$，表示为 `10000000`（为了便于说明，我们这里只写 8 位而不是 32 位）。
- 知道正数 `x` 的二进制记号，就能得到 `-x` 的二进制记号：`~x + 1`。
- `-1` 表示为 `~1 + 1 = 11111110 + 00000001 = 11111111`。
- `-42` 表示为 `~42 + 1 = 11010101 + 00000001 = 11010110`。
- 数 `-1 = 11111111` 的下一个数是 `0 = -1 + 1 = 11111111 + 00000001 = 00000000`。

这种编码的主要优点是，把无符号整数转换成有符号整数时你几乎不用做任何事（也许只需检查溢出），而且大多数运算都可以复用同一套电路，可能只需要在比较等操作时翻转符号位。

话虽如此，你还是需要小心有符号整数溢出。尽管它们的溢出方式几乎总是与无符号整数相同，但编程语言通常把溢出的可能性视为未定义行为。如果你需要让整数变量溢出，就把它们转换成无符号整数：反正这是免费的。

### 整数类型

整数有不同的尺寸，但功能大致相同。

| 位数 | 字节数 | 有符号 C 类型 | 无符号 C 类型 | 汇编 |
|-----:|-------|----------------------|----------------------|----------|
|    8 | 1     | `signed char`[^char] | `unsigned char`      | `byte`   |
|   16 | 2     | `short`              | `unsigned short`     | `word`   |
|   32 | 4     | `int`                | `unsigned int`       | `dword`  |
|   64 | 8     | `long long`          | `unsigned long long` | `qword`  |

[^char]: 注意，`char`、`unsigned char`、`signed char` 在技术上是三种不同的类型。C 标准把普通 `char` 是否有符号留给实现决定（在大多数编译器上，它是有符号的）。

整数的各个位只是按顺序存储。这里唯一的歧义是存储的顺序——从左到右还是从右到左——称为*字节序（endianness）*。根据架构的不同，格式可以是：

- *小端序（little-endian）*，先存放*较低*的位。例如，$42_{10}$ 会存成 $010101$。
- *大端序（big-endian）*，先存放*较高*的位。本文之前的例子都遵循这种格式。

这看起来是一个重要的架构特性，但在大多数情况下它并没有影响：随便选一种风格并坚持用下去就行。但在某些情况下它确实有影响：

- 小端序的优点在于，你可以只加载更少的字节就把一个值转成更小的类型（例如把 `long long` 转成 `int`），在大多数情况下这意味着什么都不用做——多亏了*寄存器别名（register aliasing）*，`eax` 指向 `rax` 的前 4 个字节，所以转换几乎是免费的。读取各种类型大小的值也更容易——而在大端序架构上，从 `long long` 数组中加载一个 `int` 需要把指针移动 2 个字节。
- 大端序的优点在于高字节先被加载，理论上可以让从高到低的例程（如比较和打印）更快。你还可以只加载第一个字节就完成某些检查，例如判断一个数是否为负。

大端序也更“自然”——我们在纸上写二进制数时就是这样写的——但更快类型转换的优势胜过了它。因此，大多数硬件默认使用小端序，不过有些 CPU 是“双端序（bi-endian）”的，可以配置为按需切换模式。

### 128 位整数

有时我们需要把两个 64 位整数相乘得到 128 位整数——通常只是作为临时值，紧接着就对一个 64 位整数取模。

没有 128 位寄存器来保存这种乘法的结果，因此 `mul` 指令除了普通的 `mul r r` 形式（将寄存器中的值相乘并保留结果的低半部分）之外，还有另一种 `mul r` 模式：它把 `rax` 寄存器中存放的值与操作数相乘，并把结果写入两个寄存器——结果的低 64 位进入 `rax`，高 64 位进入 `rdx`：

```nasm
; input: 64-bit integers a and b, stored in rsi and rdi
; output: 128-bit product a * b, stored in rax (lower 64-bit) and rdx (higher 64-bit)
mov     rax, rdi
mov     r8, rdx
imul    rsi
```

一些编译器有支持这种操作的独立类型。在 GCC 和 Clang 中，它以 `__int128` 的形式提供：

```cpp
void prod(int64_t a, int64_t b, __int128 *c) {
    *c = a * (__int128) b;
}
```

它的典型用法是立即取出乘法的低半部分或高半部分，然后不再管它：

```c++
__int128_t x = 1;
int64_t hi = x >> 64;
int64_t lo = (int64_t) x; // will be just truncated
```

除了乘法之外，128 位整数在所有用途下都只是捆绑在一起的两个寄存器。这让一个功能完整的 128 位类型显得过于怪异，所以除基本算术运算之外，对它的支持很有限。例如：

```c++
__int128_t add(__int128_t a, __int128_t b) {
    return a + b;
}
```

会被编译成：

```nasm
add:
    mov rax, rdi
    add rax, rdx    ; this sets the carry flag in case of an overflow
    adc rsi, rcx    ; +1 if the carry flag is set
    mov rdx, rsi
    ret
```

其他平台也提供了类似机制来处理超出字长的乘法。例如，Arm 有 `mulhi` 和 `mullo` 指令，分别返回乘法的低半部分和高半部分，而 x86 的 [SIMD 扩展](/hpc/simd)也有类似的 32 位指令。
