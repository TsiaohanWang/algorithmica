浮点运算的用户配得上一种 IQ 钟形曲线梗图——因为大多数人跟它的关系通常就是这样演进的：

- 初学编程的人到处使用它，好像它是什么拥有无限精度的魔法数据类型。
- 然后他们发现 `0.1 + 0.2 != 0.3` 之类的怪癖，抓狂不已，开始以为每次计算都会被加上某个随机的误差项，并在很多年里完全避开任何实数类型。
- 最后他们终于振作起来，读了 IEEE-754 浮点数的规范，开始正确地使用它们。

遗憾的是，还有太多人停留在第 2 阶段，孕育着关于浮点运算的各种误解——认为它本质上不精确、不稳定，而且比整数运算慢。

![](../img/iq.svg)

但这些都只是迷思。浮点运算由于有专用指令，通常比整数运算*更快*；而且实数表示经过了彻底标准化，在舍入方面遵循简单而确定性的规则，让你能够可靠地管理计算误差。

事实上，它如此可靠，以至于一些高级编程语言——最著名的是 JavaScript——根本没有整数。在 JavaScript 中只有一种 `number` 类型，内部以 64 位 `double` 存储；由于浮点运算的工作方式，$[-2^{53}, 2^{53}]$ 之间的所有整数以及涉及它们的计算结果都能被精确存储，因此从程序员的角度看，几乎没有单独设立整数类型的实际需要。

一个值得注意的例外是当你需要对数字执行位运算时——*浮点运算单元（floating-point unit）*（负责浮点数运算的协处理器）通常不支持这种操作。这时就需要把数字转换成整数。这个操作在启用 JavaScript 的浏览器中使用极其频繁，以至于 arm 专门[增加了一条 "FJCVTZS" 指令](https://community.arm.com/developer/ip-products/processors/b/processors-ip-blog/posts/armv8-a-architecture-2016-additions)，全称是 "Floating-point Javascript Convert to Signed fixed-point, rounding toward Zero"（浮点 JavaScript 转换为有符号定点数，向零舍入），它的作用正如其名——以与 JavaScript 完全相同的方式把实数转换为整数——这是软硬件反馈循环在现实中的一个有趣例子。

不过，除非你是那种纯粹用实数类型来模拟整数运算的 JavaScript 开发者，否则你很可能需要一份更深入的浮点运算指南，所以我们先从更宽泛的主题讲起。

## 实数的表示

如果你需要处理实数（非整数），你有几种适用性各异的方案。在直接跳到浮点数（本文大部分内容的主角）之前，我们想先讨论现有的替代方案及其背后的动机——毕竟，回避浮点运算的人确实有他们的道理。

### 符号表达式

第一种也是最笨重的方法：不存储结果值本身，而是存储产生它们的代数表达式。

这里有一个简单的例子。在某些应用中，比如计算几何，除了加、减、乘之外，你还需要不经过舍入的除法，得到有理数，它能用两个整数之比精确表示：

```c++
struct r {
    int x, y;
};

r operator+(r a, r b) { return {a.x * b.y + a.y * b.x, a.y * b.y}; }
r operator*(r a, r b) { return {a.x * b.x, a.y * b.y}; }
r operator/(r a, r b) { return {a.x * b.x, a.y * b.y}; }
bool operator<(r a, r b) { return a.x * b.y < b.x * a.y; }
// ...and so on, you get the idea
```

这个比值可以被化为既约形式，这甚至能让这种表示唯一：

```c++
struct r {
    int x, y;
    r(int x, int y) : x(x), y(y) {
        if (y < 0)
            x = -x, y = -y;
        int g = gcd(x, y);
        x /= g;
        y /= g;
    }
};
```

WolframAlpha 和 SageMath 这类*计算机代数（computer algebra）*系统正是这样工作的：它们只对符号表达式进行操作，避免把任何东西当作实数值来求值。

用这种方法，你能获得绝对精度，在范围有限（比如只支持有理数）时它表现良好。但代价是巨大的计算开销，因为一般情况下，你需要以某种方式存储产生结果的整段操作历史，并在每次执行新操作时把它考虑进去——随着历史的增长，这会迅速变得不可行。

### 定点数

另一种做法是坚持使用整数，但把它们当作乘以某个固定常数的值。这本质上相当于把计量单位换成更适配当前量级的单位。

由于有些值无法精确表示，这会使得计算不精确：你需要把结果舍入到最近的可表示值。

这种方法常用于金融软件，在那里你*确实*需要一种直截了当的方式来管理舍入误差，好让最后的数字能对得上。例如，纳斯达克在股票报价中以一美元的 $\frac{1}{10000}$ 作为基本单位，也就是说所有交易中小数点后都恰好有 4 位数字的精度。

```c++
struct money {
    uint v; // 1/10000th of a dollar
};

std::string to_string(money) {
    return std::format("${0}.{1:04d}", v / 10000, v % 10000);
}

money operator*(money x, money y) { return {x.v * y.v / 10000}; }
```

除了引入舍入误差之外，更大的问题是当比例常数放错位置时，它们就变得毫无用处。如果你处理的数太大，内部整数值会溢出；如果数太小，它们会被直接舍入成零。有趣的是，前一种情况曾在纳斯达克[引发过问题](https://www.wsj.com/articles/berkshire-hathaways-stock-price-is-too-much-for-computers-11620168548)：当时伯克希尔·哈撒韦的股价逼近 $\frac{2^{32} - 1}{10000}$ = 429,496.7295 美元，再也装不进无符号 32 位整数。

这个问题使得定点算术根本不适合那些需要同时使用很小和很大数字的应用，例如计算某些物理方程：

$$
E = m c^2
$$

在这个例子中，$m$ 通常与质子的质量（$1.67 \cdot 10^{-27}$ kg）处于同一数量级，而 $c$ 是光速（$3 \cdot 10^9$ m/s）。

### 浮点数

在大多数数值应用中，我们主要关心的是相对误差。我们希望计算的结果与真实值相差不超过，比如说，$0.01\\%$，而且我们并不真的在乎这 $0.01\\%$ 在绝对单位下相当于多少。

浮点数解决这个问题的方法，是存储一定数量的最高有效位数字以及这个数的数量级。更准确地说，它们用一个整数（称为*有效数（significand）*或*尾数（mantissa）*）表示，并用某个固定底数的指数进行缩放——最常见的是 2 或 10。例如：

$$
1.2345 =
\underbrace{12345}_\text{尾数}
\times {\underbrace{10}_\text{底数}\!\!\!\!}
      ^{\overbrace{-4}^\text{指数}}
$$

计算机以定长的二进制字运算，因此在为硬件设计浮点格式时，你希望采用定长的二进制格式，一部分位留给尾数（以获得更高精度），一部分位留给指数（以获得更大范围）。

这个手工实现的浮点数大概能传达这个想法：

```cpp
// DIY floating-point number
struct fp {
    int m; // mantissa
    int e; // exponent
};
```

这样我们就能表示形如 $\pm \\; m \times 2^e$ 的数，其中 $m$ 和 $e$ 都是有界*且可能为负*的整数——分别对应负数或很小的数。这些数的分布非常不均匀：$[0, 1)$ 范围内的数大约与 $[1, +\infty)$ 范围内的数一样多。

注意，某些数的这种表示并不唯一。例如，数字 $1$ 可以表示为

$$
1 \times 2^0 = 2 \times 2^{-1} = 256 \times 2^{-8}
$$

以及另外 28 种不会让尾数溢出的方式。

这对某些应用（如比较或哈希）来说可能是个问题。为了解决它，我们可以用某种约定来*规范化*这些表示。在十进制中，[标准形式](https://en.wikipedia.org/wiki/Scientific_notation)是始终把小数点放在第一个数字之后（`6.022e23`），对二进制我们也可以这样做：

$$
42 = 10101_2 = 1.0101_2 \times 2^5
$$

注意，按照这个规则，第一位总是 1。显式存储它是多余的，所以我们干脆假装它在那里，只存储其余位，它们对应 $[0, 1)$ 范围内的某个有理数。现在可表示的数的集合大致为

$$
\{ \pm \; (1 + m) \cdot 2^e \; | \; m = \frac{x}{2^{32}}, \; x \in [0, 2^{32}) \}
$$

由于 $m$ 现在是非负值，我们把它改成无符号整数，并另外添加一个布尔字段来存放数的符号：

```cpp
struct fp {
    bool s;     // sign: "0" for "+", "1" for "-" 
    unsigned m; // mantissa
    int e;      // exponent
};
```

现在，让我们尝试用手工浮点数实现某种算术运算——例如乘法。使用新的公式，结果应为：

$$
\begin{aligned}
c  &= a \cdot b
\\ &= (s_a \cdot (1 + m_a) \cdot 2^{e_a}) \cdot (s_b \cdot (1 + m_b) \cdot 2^{e_b})
\\ &= s_a \cdot s_b \cdot (1 + m_a) \cdot (1 + m_b) \cdot 2^{e_a} \cdot 2^{e_b} 
\\ &= \underbrace{s_a \cdot s_b}_{s_c} \cdot (1 + \underbrace{m_a + m_b + m_a \cdot m_b}_{m_c}) \cdot 2^{\overbrace{e_a + e_b}^{e_c}}
\end{aligned}
$$

这些分组现在看起来可以直接计算了，但有两个细微之处：

- 新的尾数现在位于 $[0, 3)$ 范围内。我们需要检查它是否大于 $1$ 并对表示进行规范化，应用下面的公式：$1 + m = (1 + 1) + (m - 1) = (1 + \frac{m - 1}{2}) \cdot 2$。
- 由于精度不足，结果很可能无法精确表示。我们需要两倍的位数来容纳 $m_a \cdot m_b$ 这一项，这里我们最多只能把它舍入到最近的可表示数。

由于我们需要一些额外的位来正确处理尾数溢出问题，我们将从 $m$ 中预留一个位，从而把它限制在 $[0,2^{31})$ 范围内。

```c++
fp operator*(fp a, fp b) {
    fp c;
    c.s = a.s ^ b.s;
    c.e = a.e + b.e;
    
    uint64_t x = a.m, y = b.m; // casting to wider types
    uint64_t m = (x << 31) + (y << 31) + x * y; // 62- or 63-bit intermediate result
    if (m & (1<<62)) { // checking for overflow
        m -= (1<<62); // m -= 1;
        m >>= 1;
        c.e++;
    }
    m += (1<<30); // "rounding" by adding 0.5 to a value that will be floored next
    c.m = m >> 31;
    
    return c;
}
```

许多需要更高精度的应用以类似的方式使用软件浮点运算。但当然，你不会想在每次要乘两个实数时执行这段代码编译出的十来条指令，因此在现代 CPU 上，浮点运算都是在硬件中实现的——由于它的复杂性，通常作为独立的协处理器。

x86 的*浮点运算单元*（通常称为 x87）拥有独立的寄存器和自己的一套小型指令集，支持内存操作、基本算术、三角函数，以及对数、指数、平方根等常见运算。为了让这些运算能正确地协同工作，还需要澄清浮点数表示的一些额外细节——我们将在[下一节](../ieee-754)中讨论。
