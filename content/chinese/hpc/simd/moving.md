如果你花过一些时间研究[这份参考](https://software.intel.com/sites/landingpage/IntrinsicsGuide)，你可能会注意到，向量操作基本上可以分为两大类：

1. 执行某种逐元素操作的指令（`+`、`*`、`<`、`acos` 等）。
2. 加载、存储、掩蔽、混洗以及一般性地搬运数据的指令。

虽然使用逐元素指令很容易，但 SIMD 最大的挑战是先把数据弄进向量寄存器，而且开销要足够低，使这整个努力物有所值。

### 对齐的加载与存储

把 SIMD 寄存器的内容读写到内存的操作各有两种版本：`load` / `loadu` 和 `store` / `storeu`。这里的字母「u」代表「未对齐」（unaligned）。区别在于，前者只有在读写块完全位于单条[缓存行](/hpc/cpu-cache/cache-lines)内时才正确工作（否则会崩溃），而后者无论哪种情况都能工作，但如果块跨越缓存行会有一点性能损失。

有时候，特别是当「内部」操作非常轻量时，这个性能差异会变得显著（至少因为你需要取回两条缓存行而不是一条）。举一个极端的例子，像这样把两个数组相加：

```c++
for (int i = 3; i + 7 < n; i += 8) {
    __m256i x = _mm256_loadu_si256((__m256i*) &a[i]);
    __m256i y = _mm256_loadu_si256((__m256i*) &b[i]);
    __m256i z = _mm256_add_epi32(x, y);
    _mm256_storeu_si256((__m256i*) &c[i], z);
}
```

……比对齐版本慢约 30%：

```c++
for (int i = 0; i < n; i += 8) {
    __m256i x = _mm256_load_si256((__m256i*) &a[i]);
    __m256i y = _mm256_load_si256((__m256i*) &b[i]);
    __m256i z = _mm256_add_epi32(x, y);
    _mm256_store_si256((__m256i*) &c[i], z);
}
```

在第一个版本中，假设数组 `a`、`b` 和 `c` 都是 64 字节*对齐*的（它们首元素的地址能被 64 整除，因此从缓存行开头开始），那么大约一半的读和写会是「坏的」，因为它们跨越了缓存行边界。

注意，这个性能差异是由缓存系统造成的，而不是指令本身。在大多数现代架构上，只要块只跨越一条缓存行，`loadu` / `storeu` 内建函数就应该和 `load` / `store` 一样快。后者的优势在于，它们可以充当免费的运行时断言，保证所有读写都是对齐的。

这使得在分配时正确[对齐](/hpc/cpu-cache/alignment)数组和其他数据变得很重要，这也是编译器不能总是高效[自动向量化](../auto-vectorization)的原因之一。对大多数用途来说，我们只需要保证任意 32 字节的 SIMD 块不会跨越缓存行边界，而我们可以用 `alignas` 说明符来指定这种对齐：

<!--

默认情况下，当你分配一个数组时，你得到的关于对齐的唯一保证是：没有任何元素会被缓存行切分。对于 `int` 数组，这意味着它获得 4 字节（`sizeof int`）的对齐，这样读取任一元素时只需加载恰好一条缓存行。为了我们的目的，我们希望保证任意（256 位 = 32 字节）SIMD 块都不会被切分，因此需要指定 32 字节的对齐。对于静态数组，我们可以用 `alignas` 说明符做到这一点：

-->

```c++
alignas(32) float a[n];

for (int i = 0; i < n; i += 8) {
    __m256 x = _mm256_load_ps(&a[i]);
    // ...
}
```

[内置向量类型](../intrinsics)已经有相应的对齐要求，并假定内存读写是对齐的——因此分配 `v8si` 数组时你总是安全的，但从 `int*` 转换过来时，你必须确保它是对齐的。

与标量情况类似，许多算术指令把内存地址作为操作数——[向量加法](../intrinsics)就是一个例子——尽管你不能把它显式地用作内建函数，而必须依赖编译器。还有一些其他指令用于从内存读取 SIMD 块，尤其是[非临时（non-temporal）](/hpc/cpu-cache/bandwidth#bypassing-the-cache)的加载和存储操作，它们不会把访问的数据提升到缓存层级中。

### 寄存器别名

第一个 SIMD 扩展 MMX 起步时规模很小。它只使用 64 位向量，这些向量被巧妙地与[80 位浮点数](/hpc/arithmetic/ieee-754)的尾数部分做了别名映射，从而无需引入一组单独的寄存器。随着后续扩展使向量尺寸不断增大，通用寄存器中使用的同一种[寄存器别名](/hpc/architecture/assembly#instructions-and-registers)机制也被用于向量寄存器，以维持向后兼容：`xmm0` 是 `ymm0` 的前半部分（128 位），`xmm1` 是 `ymm1` 的前半部分，依此类推。

这个特性，加上向量寄存器位于 FPU 之中这一事实，使得在它们与通用寄存器之间搬运数据稍微有些复杂。

### 提取与插入

要从向量中*提取*（extract）某个特定值，可以使用 `_mm256_extract_epi32` 及类似的内建函数。它以要提取的整数的索引作为第二个参数，并根据该值生成不同的指令序列。

如果你需要提取第一个元素，它会生成 `vmovd` 指令（针对 `xmm0`，即向量的前半部分）：

```nasm
vmovd eax, xmm0
```

对于 SSE 向量的其他元素，它会生成可能稍慢一些的 `vpextrd`：

```nasm
vpextrd eax, xmm0, 1
```

要从 AVX 向量的后半部分提取任何元素，它必须先提取那后半部分，然后才是标量本身。例如，下面是这样提取最后一个（第八个）元素的：

```nasm
vextracti128 xmm0, ymm0, 0x1
vpextrd      eax, xmm0, 3
```

还有一个类似的 `_mm256_insert_epi32` 内建函数，用来覆写特定元素：

```nasm
mov          eax, 42

; v = _mm256_insert_epi32(v, 42, 0);
vpinsrd xmm2, xmm0, eax, 0
vinserti128     ymm0, ymm0, xmm2, 0x0

; v = _mm256_insert_epi32(v, 42, 7);
vextracti128 xmm1, ymm0, 0x1
vpinsrd      xmm2, xmm1, eax, 3
vinserti128  ymm0, ymm0, xmm2, 0x1
```

要点：在向量寄存器与标量数据之间往返搬运是很慢的，尤其当目标不是第一个元素时。

### 生成常量

如果你需要填充的不只是一个元素，而是整个向量，可以使用 `_mm256_setr_epi32` 内建函数：

```c++
__m256 iota = _mm256_setr_epi32(0, 1, 2, 3, 4, 5, 6, 7);
```

这里的「r」代表「反向」（reversed）——是从[CPU 的视角](/hpc/arithmetic/integer#integer-types)来看，而不是从人类的视角。还有不带「r」的 `_mm256_set_epi32`，它从相反的方向填充值。两者大多用于创建编译期常量，然后通过一次块加载取进寄存器。如果你的用途是把向量填成零，请改用 `_mm256_setzero_si256`：它把寄存器与自身做 `xor`。

在内置向量类型中，你只需使用普通的括号初始化：

```c++
vec zero = {};
vec iota = {0, 1, 2, 3, 4, 5, 6, 7};
```

### 广播

除了只修改一个元素，你还可以把单个值*广播*（broadcast）到向量的所有位置：

```nasm
; __m256i v = _mm256_set1_epi32(42);
mov          eax, 42
vmovd        xmm0, eax
vpbroadcastd ymm0, xmm0
```

这是一个经常使用的操作，因此你也可以使用一个内存位置：

```nasm
; __m256 v = _mm256_broadcast_ss(&a[i]);
vbroadcastss ymm0, DWORD PTR [rdi]
```

使用内置向量类型时，你可以创建一个零向量，然后加上一个标量：

```c++
vec v = 42 + vec{};
```

### 映射到数组

如果你想避开所有这些复杂性，可以直接把向量倾倒进内存，再把它的值作为标量读回来：

```c++
void print(__m256i v) {
    auto t = (unsigned*) &v;
    for (int i = 0; i < 8; i++)
        std::cout << std::bitset<32>(t[i]) << " ";
    std::cout << std::endl;
}
```

这可能不快，在技术上也可能不合法（C++ 标准没有规定像这样强制转换数据会发生什么），但它很简单，我在调试时经常用这段代码打印出向量的内容。

### 非连续加载

后来的 SIMD 扩展加入了特殊的「gather」和「scatter」指令，它们使用任意的数组索引非顺序地读写数据。不过它们并不会快 8 倍，而且通常受内存而不是 CPU 的限制，但对于某些应用（如稀疏线性代数）仍然很有用。

gather 自 AVX2 起可用，各种 scatter 指令自 AVX512 起可用。

![](../img/gather-scatter.png)

让我们看看它们是否比标量读取更快。首先，我们创建一个大小为 $N$ 的数组和 $Q$ 个随机读取查询：

```c++
int a[N], q[Q];

for (int i = 0; i < N; i++)
    a[i] = rand();

for (int i = 0; i < Q; i++)
    q[i] = rand() % N;
```

在标量代码中，我们逐个把查询指定的元素加到校验和上：

```c++
int s = 0;

for (int i = 0; i < Q; i++)
    s += a[q[i]];
```

而在 SIMD 代码中，我们用 `gather` 指令并行地对 8 个不同的索引做同样的事：

```c++
reg s = _mm256_setzero_si256();

for (int i = 0; i < Q; i += 8) {
    reg idx = _mm256_load_si256( (reg*) &q[i] );
    reg x = _mm256_i32gather_epi32(a, idx, 4);
    s = _mm256_add_epi32(s, x);
}
```

它们的表现大致相同，除非数组能装进 L1 缓存：

![](../img/gather.svg)

`gather` 和 `scatter` 的目的不是更快地执行内存操作，而是把数据弄进寄存器，以便对它们进行重计算。对于任何比一次加法更昂贵的操作，它们都极其有利。

（快速）gather 和 scatter 指令的缺失，使得 CPU 上的 SIMD 编程与支持独立内存访问的真正并行计算环境大不相同。你总得绕着它做工程，采用各种方式把数据组织成顺序结构，以便能加载进寄存器。
