SIMD 并行最常用于*易并行*（embarrassingly parallel）的计算：这类计算的全部工作就是把某个逐元素函数应用到数组的每个元素上，再把结果写到别处。在这种情况下，你甚至不需要了解 SIMD 是如何工作的：编译器完全能够自行优化这类循环——你只需要知道存在这样一种优化，而且它通常能带来 5–10 倍的加速。

什么都不做、依赖自动向量化，实际上是使用 SIMD 最流行的方式。事实上，在很多情况下，甚至建议坚持使用朴素的标量代码，因为它更简单、更易维护。

但即便是那些看起来很容易向量化的循环，也常常因为一些技术细节而得不到优化。[和许多其他情况一样](/hpc/compilation/contracts)，编译器可能需要程序员提供一些额外信息，因为程序员对问题的了解可能比静态分析能推断出来的稍多一些。

### 潜在问题

考虑我们[最初](../intrinsics/#simd-intrinsics)给出的那个「a + b」示例：

```c++
void sum(int *a, int *b, int *c, int n) {
    for (int i = 0; i < n; i++)
        c[i] = a[i] + b[i];
}
```

让我们站在编译器的立场上，想想这个循环被向量化时可能出现什么问题。

**数组大小**。如果数组大小事先未知，那么它可能从一开始就太小，向量化无利可图。即使数组足够大，我们也需要为循环的剩余部分插入额外的运行时检查，用标量方式处理它，这会花费一次分支。

要消除这些运行时检查，请使用编译期常量的数组大小，并最好把数组填充到最接近的 SIMD 块大小的整数倍。

**内存别名（memory aliasing*）*。即使数组大小不成问题，对这个循环做向量化在技术上也不总是正确的。例如，数组 `a` 和 `c` 可能以起始位置只差一个元素的方式相交——谁知道呢，也许程序员就是想用这种方式通过卷积计算斐波那契序列。在这种情况下，SIMD 块中的数据会相互重叠，观察到的行为将与标量版本不同。

当编译器无法证明这个函数绝不会被用于相交的数组时，它就必须生成两个实现变体——一个向量化的和一个「安全」的——并插入运行时检查来在两者之间选择。为了避免这些检查，我们可以通过添加 `__restrict__` 关键字告诉编译器不存在内存别名：

```cpp
void add(int * __restrict__ a, const int * __restrict__ b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

另一种方式（SIMD 特有的）是「忽略向量依赖」编译指令。它是一种通用的方法，用来告知编译器循环的各次迭代之间不存在依赖关系：

```c++
#pragma GCC ivdep
for (int i = 0; i < n; i++)
    // ...
```

**对齐**。编译器对这些数组的对齐情况也一无所知，因此它要么在开始向量化部分之前先处理数组开头的若干元素，要么使用[未对齐的内存访问](../moving)而损失一些性能。

为了帮助编译器消除这种边界情况，我们可以在静态数组上使用 `alignas` 说明符，并用 `std::assume_aligned` 函数把指针标记为已对齐。

**检查向量化是否真的发生**。无论哪种情况，检查编译器是否按你的意图对循环进行了向量化都是有用的。你可以把代码[编译成汇编](/hpc/compilation/stages)，查找以「v」开头的指令块；也可以加上 `-fopt-info-vec-optimized` 编译选项，让编译器指出自动向量化发生在哪里、使用了多宽的 SIMD。如果把这个选项中的 `optimized` 换成 `missed` 或 `all`，你还能得到其他地方没有向量化的原因。

还有[许多其他方法](https://software.intel.com/sites/default/files/m/4/8/8/2/a/31848-CompilerAutovectorizationGuide.pdf)可以精确地告诉编译器我们的意图，但在特别复杂的情况下——例如循环内部有大量分支或函数调用时——更简单的做法是往下走一层抽象，手动向量化。

### SPMD

在自动向量化和手动使用 SIMD 内建函数之间，有一个巧妙的折中方案：「单程序多数据」（single program, multiple data，SPMD）。这是一种计算模型：程序员写出来的看起来是一个普通的串行程序，但它在硬件上实际上是并行执行的。

编程体验大体相同，而且仍然存在计算必须是数据并行的根本限制，但 SPMD 保证了无论编译器或目标 CPU 架构如何，向量化都会发生。它还允许计算自动并行到多个核心上，在某些情况下甚至能卸载到其他类型的并行硬件上。

一些现代语言（[Julia](https://docs.julialang.org/en/v1/base/base/#Base.SimdLoop.@simd)）、多处理 API（[OpenMP](https://www.openmp.org/spec-html/5.0/openmpsu42.html)）和专用编译器（Intel [ISPC](https://ispc.github.io/)）都支持 SPMD，但它最大的成功是在 GPU 编程领域——在那里，问题和硬件都是大规模并行的。
