`-O2` 和 `-O3` 启用的大多数编译器优化都保证能提升性能，或者至少不会严重损害性能。那些没有被包含在 `-O3` 里的优化，要么不是严格符合标准的，要么高度依赖具体场合，需要程序员提供一些额外输入来帮助判断使用它们是否有利。

让我们讨论其中最常用、且本书前文已经介绍过的几个。

### 循环展开

[循环展开](/hpc/architecture/loops#loop-unrolling)默认是关闭的，除非循环的迭代次数是一个编译期已知的小常量——在这种情况下，它会被替换成一段完全无跳转的、重复的指令序列。可以通过 `-funroll-loops` 标志全局启用，它会展开所有迭代次数可在编译期或进入循环时确定的循环。

你也可以用 pragma 针对某个特定循环：

```c++
#pragma GCC unroll 4
for (int i = 0; i < n; i++) {
    // ...
}
```

循环展开会使二进制文件变大，至于会不会跑得更快则不一定。不要狂热地使用它。

### 函数内联

[内联](/hpc/architecture/functions#inlining)最好留给编译器来决定，但你可以用 `inline` 关键字影响它：

```c++
inline int square(int x) {
    return x * x;
}
```

不过，如果编译器认为潜在的性能收益不值得，这个提示可能被忽略。你可以通过添加 `always_inline` 属性来强制内联：

```c++
#define FORCE_INLINE inline __attribute__((always_inline))
```

还有一个 `-finline-limit=n` 选项，可以让你为被内联函数的大小设定一个具体阈值（按指令条数计）。它在 Clang 中的等价物是 `-inline-threshold`。

### 分支可能性

分支的[可能性](/hpc/architecture/layout#unequal-branches)可以用 `[[likely]]` 和 `[[unlikely]]` 属性在 `if` 和 `switch` 中给出提示：

```c++
int factorial(int n) {
    if (n > 1) [[likely]]
        return n * factorial(n - 1);
    else [[unlikely]]
        return 1;
}
```

这是仅在 C++20 中才出现的新特性。在此之前，有一些编译器特有的内建函数（intrinsics）被用来包裹条件表达式。同样的例子在老版本 GCC 中是这样的：

```c++
int factorial(int n) {
    if (__builtin_expect(n > 1, 1))
        return n * factorial(n - 1);
    else
        return 1;
}
```

诸如此类需要你把编译器指向正确方向的情况还有很多，但我们等到它们变得更加相关时再讨论。

### 性能剖析引导优化

往源代码里添加所有这些元数据是件繁琐的事。人们本来就已经够讨厌写 C++ 了，更别说还要做这些。

而且，某些优化是否有益也并不总是显而易见的。要就分支重排、函数内联或循环展开做出决定，我们需要回答诸如此类的问题：

- 这个分支被走到的频率有多高？
- 这个函数被调用的频率有多高？
- 这个循环的平均迭代次数是多少？

幸运的是，有一种方法可以自动提供这些真实世界的信息。

*性能剖析引导优化*（Profile-guided optimization，PGO，也叫「pogo」，因为念起来更容易也更有趣）是一种利用[性能剖析数据](/hpc/profiling)来超越纯静态分析所能达到的性能的技术。简而言之，它涉及在程序中的关注点处添加计时器和计数器，用真实数据编译并运行程序，然后再次编译——但这次把测试运行中获得的信息提供给编译器。

整个过程由现代编译器自动化完成。例如，`-fprofile-generate` 标志会让 GCC 用性能剖析代码对程序进行插桩：

```
g++ -fprofile-generate [other flags] source.cc -o binary
```

在我们运行这个程序之后——最好是在尽可能代表真实使用场景的输入上运行——它会生成一堆包含测试运行日志数据的 `*.gcda` 文件，之后我们可以重新构建程序，只不过这次加上 `-fprofile-use` 标志：

```
g++ -fprofile-use [other flags] source.cc -o binary
```

对于大型代码库，它通常能将性能提升 10-20%，正因如此，它常被包含在性能关键型项目的构建流程中。这也是一条更有理由投资于扎实的基准测试代码的理由。
