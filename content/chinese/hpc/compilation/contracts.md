在 Java 和 Rust 这类「安全」语言中，通常每一种可能的操作、每一种可能的输入都有定义良好的行为。确实有一些*定义不完整*的东西，比如哈希表中键的顺序，或者 `std::vector` 的增长因子，但这些通常只是些细枝末节，留给实现去决定，以便将来获得潜在的性能收益。

相比之下，C 和 C++ 把未定义行为（undefined behavior）的概念提升到了另一个层面。某些操作在编译期或运行期并不会引发错误，只是不被*允许*——从程序员与编译器之间存在*契约*的意义上说：一旦发生未定义行为，编译器在法律上被允许做任何事，包括炸掉你的显示器或格式化你的硬盘。不过编译器工程师对此并不感兴趣。相反，未定义行为被用来保证不存在边界情况，并帮助优化。

### 未定义行为为何存在

会造成未定义行为的操作主要有两类：

- 几乎可以肯定是无意之失的 bug 类操作，比如除以零、解引用空指针、读取未初始化的内存。你希望在测试阶段尽早抓住这些问题，所以让程序崩溃或出现某种不确定的行为，比让它们总是执行一个固定的兜底动作（比如返回零）要好。

  你可以用*消毒器*（sanitizers）编译并运行程序，以便尽早捕获未定义行为。在 GCC 和 Clang 中，可以使用 `-fsanitize=undefined` 标志，一些以制造 UB 闻名的操作会被插桩，以便在运行时检测到它们。

- 在不同平台上可观察行为略有差异的操作。例如，把整数左移超过 31 位的结果是未定义的，因为执行该操作的指令在 Arm 和 x86 CPU 上的实现不同。如果你把某一种具体行为标准化，那么为另一个平台编译的所有程序都得额外花几个时钟周期去检查这种边界情况，所以最好还是让它保持未定义。

  有时，某些平台特定行为确实存在合理的应用场景，此时可以不把它声明为未定义，而是留作*由实现定义*（implementation-defined）。例如，[负数](/hpc/arithmetic/integer)右移的结果取决于平台：要么移入 0，要么移入 1（比如把 `11010110 = -42` 右移一位，结果可能是 `01101011 = 107`，也可能是 `11101011 = -21`，两种用法都是真实存在的）。

把某物指定为未定义行为而非实现定义行为，同样有助于编译器优化。考虑有符号整数溢出的情况。在几乎所有的架构上，[有符号整数](/hpc/arithmetic/integer)的溢出方式都与无符号整数相同：`INT_MAX + 1 == INT_MIN`。然而，按照 C++ 标准，这却是未定义行为。这完全是刻意为之：如果禁止有符号整数溢出，那么对 `int` 而言，`(x + 1) > x` 保证恒为真；但对 `unsigned int` 就不成立，因为 `(x + 1)` 可能溢出。对于有符号类型，这让编译器可以把这类检查直接优化掉。

举一个更自然的例子：考虑控制变量为整数的循环。现代 C++ 以及 Rust 这类语言鼓励程序员使用无符号整数（`size_t` / `usize`），而 C 程序员则固执地继续用 `int`。要理解其中的原因，请看下面这个 `for` 循环：

```cpp
for (unsigned int i = 0; i < n; i++) {
    // ...
}
```

这个循环会执行多少次？从技术上来说有两个都合理的答案：$n$ 次和无穷次。第二种情况发生在 $n$ 超过 $2^{32}$ 时，此时 $i$ 每 $2^{32}$ 次迭代就会重置回零。虽然前者大概才是程序员所设想的，但为了符合语言规范，编译器仍然必须插入额外的运行时检查，并考虑这两种应当被区别优化的情况。而 `int` 版本则恰好会执行 $n$ 次迭代，因为有符号溢出的可能性本身已被定义所排除。

### 消除边界情况

「安全」的编程风格通常涉及大量运行时检查，但它们不一定非要以性能为代价。

例如，Rust 以在索引数组和其他随机访问结构时进行边界检查而闻名。在 C++ STL 中，`vector` 和 `array` 有一个「不安全」的 `[]` 运算符和一个「安全」的 `.at()` 方法，后者大致长这样：

```cpp
T at(size_t k) {
    if (k >= size())
        throw std::out_of_range("Array index exceeds its size");
    return _memory[k];
}
```

有趣的是，这些检查在运行时其实很少真正执行，因为编译器往往能在编译期证明每次访问都在界内。例如，在 `for` 循环中从 1 迭代到数组大小、每一步索引第 $i$ 个元素时，不可能发生任何非法访问，因此边界检查可以被安全地优化掉。

### 假设

当编译器无法证明边界情况不存在，而*你*可以时，这份额外的信息可以通过未定义行为的机制来提供。

Clang 有一个很有用的 `__builtin_assume` 函数，你可以把一条保证为真的语句放进去，编译器会在优化时利用这个假设。在 GCC 中，可以用 `__builtin_unreachable` 达到同样的效果：

```cpp
void assume(bool pred) {
    if (!pred)
        __builtin_unreachable();
}
```

例如，你可以在上面例子中的 `at` 之前放一句 `assume(k < vector.size())`，然后边界检查就会被优化掉。

把 `assume` 与 `assert`、`static_assert` 结合起来找 bug 也相当有用：你可以在调试构建中用同一个函数检查前置条件，然后在生产构建中用它们提升性能。

### 运算

边界情况是你应当时刻留意的，尤其是在优化运算时。

对于[浮点运算](/hpc/arithmetic/float)，这个问题不太需要担心，因为你只要用 `-ffast-math` 标志（它也被包含在 `-Ofast` 中）禁用严格的标准符合性即可。你几乎必须这么做，否则编译器只能按照源码中的顺序原样执行算术运算，做不了任何优化。

对整数运算来说则不然，因为结果必须始终精确。考虑除以 2 的情况：

```cpp
unsigned div_unsigned(unsigned x) {
    return x / 2;
}
```

一个广为人知的优化是用一次右移（`x >> 1`）来替换它：

```nasm
shr eax
```

这对于所有*正*数当然是正确的，但一般情况呢？

```cpp
int div_signed(int x) {
    return x / 2;
}
```

如果 `x` 为负，那么简单的移位就不行了——无论移位时补入的是 0 还是符号位：

- 如果补入 0，我们得到的是非负结果（符号位为 0）。
- 如果补入符号位，那么舍入将朝向负无穷而不是零（`-5 / 2` 将等于 `-3` 而不是 `-2`）[^python]。

[^python]: 有趣的事实：在 Python 中，负数的整数除法不知为何会对结果向下取整，所以 `-5 // 2 = -3`，等价于 `-5 >> 1 = -3`。我怀疑 Guido van Rossum 在设计这门语言之初并没有考虑这种优化，但从理论上讲，一个充满除以 2 运算的 [JIT 编译](/hpc/complexity/languages/#compiled-languages) Python 程序可能比对应的 C++ 程序更快。

所以，对于一般情况，我们不得不插入一些拐杖来让它正常工作：

```nasm
mov  ebx, eax
shr  ebx, 31    ; extract the sign bit
add  eax, ebx   ; add 1 to the value if it is negative to ensure rounding towards zero
sar  eax        ; this one shifts in sign bits
```

当只打算处理正数的情况时，我们也可以用 `assume` 机制排除 `x` 为负的可能性，从而避免处理这个边界情况：

```cpp
int div_assume(int x) {
    assume(x >= 0);
    return x / 2;
}
```

尽管在这个具体例子里，表达「我们只期待非负数」的最好语法也许是用无符号整数类型。

正因为存在这类细微差别，在中间函数里展开代数表达式、自己手动化简运算，往往比依赖编译器去做更有利。

### 内存别名

编译器很不擅长优化涉及内存读写操作。这是因为它们常常缺乏让优化成立所需的上下文。

考虑下面的例子：

```c++
void add(int *a, int *b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

由于这个循环的每次迭代都是独立的，它可以并行执行并被[向量化](/hpc/simd)。但从技术上讲，真的可以吗？

如果数组 `a` 和 `b` 相交，就可能出问题。考虑 `b == a + 1` 的情况，即 `b` 只是从第二个元素开始对 `a` 的一个内存视图。在这种情况下，下一次迭代依赖于前一次，唯一正确的解法是顺序执行这个循环。即使程序员知道这种情况不可能发生，编译器也不得不检查这类可能性。

这就是我们拥有 `const` 和 `restrict` 关键字的原因。前者强制我们不会通过该指针变量修改内存，后者则是告诉编译器这块内存保证不会被别名引用的一种方式。

```cpp
void add(int * __restrict__ a, const int * __restrict__ b, int n) {
    for (int i = 0; i < n; i++)
        a[i] += b[i];
}
```

单独使用这些关键字进行自我文档化也同样是个好主意。

### C++ 契约

契约编程是一项未被充分利用但非常强大的技术。

有一个处于后期阶段的提案，打算以[契约属性](http://www.hellenico.gr/cpp/w/cpp/language/attributes/contract.html)的形式把契约式设计（design-by-contract）引入 C++ 标准，它在功能上等价于我们手工制作的、编译器特有的 `assume`：

```c++
T at(size_t k) [[ expects: k < n ]] {
    return _memory[k];
}
```

一共有 3 种属性——`expects`、`ensures` 和 `assert`——分别用于在函数中指定前置条件和后置条件，以及可以放在程序中任何位置的通用断言。

遗憾的是，这个令人兴奋的新特性[尚未最终标准化](https://www.reddit.com/r/cpp/comments/cmk7ek/what_happened_to_c20_contracts/)，更不用说在主流 C++ 编译器中实现了。但也许再过几年，我们就能写出这样的代码：

```c++
bool is_power_of_two(int m) {
    return m > 0 && (m & (m - 1) == 0);
}

int mod_power_of_two(int x, int m)
    [[ expects: x >= 0 ]]
    [[ expects: is_power_of_two(m) ]]
    [[ ensures r: r >= 0 && r < m ]]
{
    int r = x & (m - 1);
    [[ assert: r = x % m ]];
    return r;
}
```

其他面向性能的语言也提供某种形式的契约编程，例如 [Rust](https://docs.rs/contracts/latest/contracts/) 和 [D](https://dlang.org/spec/contracts.html)。

一条通用的、与语言无关的建议是：始终[检查](../stages)编译器生成的汇编代码；如果它不是你期望的样子，就试着想想可能阻碍编译器优化的边界情况。
