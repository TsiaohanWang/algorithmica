利用内存硬件中可用的[免费并发](../mlp)，如果数据的位置可以被预测，*预取*（prefetch）下次可能访问的数据是有益的。当流水线中没有[数据或控制冒险](/hpc/pipelining/hazards)，CPU 可以在指令流中提前运行并乱序执行内存操作时，这很容易做到。

但有时内存位置并不在指令流中，却仍然可以以很高的概率被预测。在这些情况下，可以通过其他方式预取它们：

- 显式地，通过单独读取下一个数据字或同一条缓存行中的任意字节，使其提升到缓存层次结构中。
- 隐式地，通过使用简单访问模式（例如线性迭代），内存硬件可以检测到这些模式并自动开始预取。

隐藏内存延迟对达成性能至关重要，因此在本节中，我们将研究预取技术。

### 硬件预取

让我们修改[指针追逐](../latency)基准测试来展示硬件预取的效果。现在，我们以一种方式生成排列：CPU 遍历排列时会请求连续的缓存行，但缓存行内的元素仍然以随机顺序访问：

```cpp
int p[15], q[N];

iota(p, p + 15, 1);

for (int i = 0; i + 16 < N; i += 16) {
    random_shuffle(p, p + 15);
    int k = i;
    for (int j = 0; j < 15; j++)
        k = q[k] = i + p[j];
    q[k] = i + 16;
}
```

画图没有意义，因为它会是平坦的：无论数组大小如何，延迟都是 3ns。尽管指令调度器仍然无法告诉我们下一步要取什么，内存预取器可以通过观察内存访问来检测模式，并提前开始加载下一条缓存行，从而缓解延迟。

硬件预取对大多数使用场景来说足够聪明，但它只能检测简单的模式。你可以并行地向前或向后遍历多个数组，也许带小到中等步长，但也仅此而已。对于任何更复杂的情况，预取器无法弄清楚发生了什么，我们需要自己帮助它。

### 软件预取

软件预取最简单的方式是用 `mov` 或任何其他内存指令加载缓存行中的任意字节，但 CPU 有一个单独的 `prefetch` 指令，可以在不对缓存行做任何处理的情况下提升它。这条指令不是 C 或 C++ 标准的一部分，但在大多数编译器中以 `__builtin_prefetch` 内建函数的形式可用：

```c++
__builtin_prefetch(&a[k]);
```

想出一个它能派上用场的*简单*例子相当困难。要让指针追逐基准测试从软件预取中受益，我们需要构造一个排列：它同时要环绕整个数组循环、不能被硬件预取器预测，并且其下一个地址容易计算。

幸运的是，[线性同余发生器](https://en.wikipedia.org/wiki/Linear_congruential_generator)有一个性质：如果模数 $n$ 是质数，那么发生器的周期恰好是 $n$。因此，如果我们用一个以当前下标为状态的 LCG 生成排列，就得到了我们需要的所有性质：

```cpp
const int n = find_prime(N); // largest prime not exceeding N

for (int i = 0; i < n; i++)
    q[i] = (2 * i + 1) % n;
```

运行它时，性能与普通随机排列一致。但现在我们获得了前瞻的能力：

```cpp
int k = 0;

for (int t = 0; t < K; t++) {
    for (int i = 0; i < n; i++) {
        __builtin_prefetch(&q[(2 * k + 1) % n]);
        k = q[k];
    }
}
```

计算下一个地址有一些开销，但对于足够大的数组，它几乎快了两倍：

![](../img/sw-prefetch.svg)

有趣的是，我们可以预取不止一个元素，利用 LCG 函数中的这个模式：

$$
\begin{aligned}
   f(x)   &= 2 \cdot x + 1
\\ f^2(x) &= 4 \cdot x + 2 + 1
\\ f^3(x) &= 8 \cdot x + 4 + 2 + 1
\\ &\ldots
\\ f^k(x) &= 2^k \cdot x + (2^k - 1)
\end{aligned}
$$

因此，要加载第 `D` 个后续元素，我们可以这样做：

```cpp
__builtin_prefetch(&q[((1 << D) * k + (1 << D) - 1) % n]);
```

如果我们每次迭代都执行这个请求，平均将同时预取 `D` 个后续元素，使吞吐量提高 `D` 倍。忽略一些诸如 `D` 过大时整数溢出之类的问题，我们可以把平均延迟任意降低到接近计算下一个下标的代价（在这种情况下，它由[模运算](/hpc/arithmetic/division)主导）。

![](../img/sw-prefetch-others.svg)

注意这是一个人为构造的例子，在实战程序中插入软件预取，你失败的时候往往比成功的时候更多。这主要是因为你需要发出一条单独的内存指令，它可能与其他指令争用资源。与此同时，硬件预取 100% 无害，因为它只在内存和缓存总线空闲时才会激活。

进行软件预取时，你还可以指定数据需要被带到哪一级缓存——当你不确定是否会用到它，又不想把已在 L1 缓存中的内容踢出去时。你可以使用 `_mm_prefetch` 内建函数，它以整数值作为第二个参数，指定缓存层级。这与[非临时加载和存储](../bandwidth#bypassing-the-cache)结合使用时很有用。

### 推测执行

事实上，即使我们不确定接下来要执行哪条指令，由于[推测执行]，这有时也能起作用。考虑下面的例子：

```cpp
bool cond = some_long_memory_operation();

if (cond)
    do_this_fast_operation();
else
    do_that_fast_operation();
```

大多数现代 CPU 的做法是：它们不等条件计算出来，就开始求值一个（最可能的）分支。如果它们猜对了，你会进展得更快；如果猜错了，最坏的情况不过是丢弃一些无用的计算。这包括内存操作，也包括缓存系统——因为，反正我们都要等一百个周期，为什么不提前求值至少一个分支呢。顺便说一句，这就是 Meltdown 漏洞的由来。
