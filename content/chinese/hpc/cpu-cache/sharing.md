---
title: 内存共享
weight: 3
---

从层次结构的某一层开始，缓存会在不同核心之间*共享*。这减少了总芯片面积，让你能在单个芯片上放置更多核心，但也带来了一些「吵闹邻居」问题，因为它限制了单个执行线程可用的有效缓存大小和带宽。

在大多数 CPU 上，只有最后一层缓存是共享的，而且并不总是均匀共享。在我的机器上，有 8 个物理核心，L3 缓存大小为 8M，但它被分成两半：两组各 4 个核心只能访问自己在 L3 缓存中 4M 的区域，而不是全部。

还有更复杂的拓扑，访问内存的某些区域需要非常数的时间，对每个核心都不同（这[有时是意外的](https://randomascii.wordpress.com/2022/01/12/5-5-mm-in-1-25-nanoseconds/)）。这种架构特性被称为*非均匀内存访问*（non-uniform memory access，NUMA），多插槽系统（安装有多个独立 CPU 芯片）就是这种情况。

在 Linux 上，可以用 `lstopo` 获取内存系统的拓扑：

![用 lstopo 生成的我的 Ryzen 7 4700U 的缓存层次结构](../img/lstopo.png)

这对并行算法有一些重要的影响：多线程内存访问的性能取决于哪些核心运行哪些执行线程。为了演示这一点，我们将并行运行[带宽基准测试](../bandwidth)。

### CPU 亲和性

我们不用修改源代码来多线程运行，而可以用 [GNU parallel](https://www.gnu.org/software/parallel/) 简单地运行多个相同的进程。为了控制哪些核心执行它们，我们用 `taskset` 设置它们的*处理器亲和性*（processor affinity）。下面这条组合命令运行 4 个进程，它们可以在 CPU 的前 4 个核心上运行：

```bash
parallel taskset -c 0,1,2,3 ./run ::: {0..3}
```

下面是改变同时运行的进程数时得到的结果：

![](../img/parallel.svg)

现在你可以看到，当数组超过 L2 缓存（每个核心私有）时，性能随着进程数增加而下降，因为核心开始竞争共享的 L3 缓存和内存。

我们特意让所有进程都在前 4 个核心上运行，因为它们共享同一个 L3 缓存。如果某些进程被调度到另一半核心上，L3 缓存的争用就会减少。操作系统不会[监控](/hpc/profiling/events)这类活动——进程在做什么是它自己的私事——所以默认情况下，它在执行期间任意地把线程分配到核心上，不关心缓存亲和性，只考虑核心负载。

让我们再运行一个基准测试，但这次把进程固定到不共享 L3 缓存的不同 4 核心组上：

```bash
parallel taskset -c 0,1 ./run ::: {0..1}  # L3 cache sharing
parallel taskset -c 0,4 ./run ::: {0..1}  # no L3 cache sharing
```

它的表现更好——仿佛可用的 L3 缓存和内存带宽翻了一倍：

![](../img/affinity.svg)

这类问题在基准测试时尤其棘手，是并行应用计时时一个巨大的噪声来源。

### 占满带宽

看一下第一张图中内存的部分，似乎随着核心增多，每个进程的吞吐量变成 ½、⅓、¼ 等等，而总带宽保持不变。但这并不完全正确：争用确实有害，但单个 CPU 核心通常无法占满全部内存带宽。

如果我们更仔细地作图，就会发现总带宽实际上随着核心数增加而增加——虽然不是成比例地，并最终趋近约 42.4 GB/s 的理论最大值：

![](../img/parallel-bandwidth.svg)

注意我们仍然指定了处理器亲和性：$k$ 线程的运行使用前 $k$ 个核心。这就是为什么从 4 个核心切换到 5 个核心时性能大幅提升：如果请求经过各自独立的 L3 缓存，你可以获得更多的内存带宽。

总的来说，要达到最大带宽，你应该总是把应用的线程对称地拆分。
