在 CPU 寄存器与内存之间的数据通路上，存在着一层*缓存*的层级结构，它们的用途是加速对常用数据的访问：离处理器越近的层级越快，但容量也越小。这里的「快」适用于两个密切相关但又彼此独立的时序指标：

- 从读写操作发起时刻到数据到达时刻之间的延迟（*延迟*，latency）。
- 单位时间内能处理的内存操作数量（*带宽*，bandwidth）。

对许多算法而言，内存带宽是缓存系统最重要的特性。同时，它也是最容易测量的，所以我们就从它开始。

在我们的实验中，我们创建一个数组并迭代它 $K$ 次，递增其中的值：

```cpp
int a[N];

for (int t = 0; t < K; t++)
    for (int i = 0; i < N; i++)
        a[i]++;
```

改变 $N$ 并相应调整 $K$，使总访问的数组单元数大致保持不变，再把总时间表示为「每秒操作数」，我们得到如下所示的图：

![竖直虚线为各缓存层的大小](../img/inc.svg)

在这张图上可以清晰地看到缓存大小：

- 当整个数组能装进最底层的缓存时，程序受 CPU 限制，而不是 L1 缓存带宽。随着数组变大，循环前几次迭代带来的开销占比变小，性能越来越接近其理论最大值 16 GFLOPS。
- 但随后性能开始下降：先是数组超出 L1 缓存时降到 12-13 GFLOPS，然后当它再也装不进 L3 缓存时，逐渐降到约 2 GFLOPS。

这种情况对许多轻量级循环来说很典型。

### 频率缩放

所有 CPU 缓存层都位于与处理器相同的微芯片上，因此带宽、延迟及其所有其他特性都随时钟频率缩放。而内存则运行在自身固定的时钟上，其特性保持不变。我们可以重新运行同样的基准测试并开启睿频，来观察这一点：

![](../img/boost.svg)

这个细节在比较算法实现时就会发挥作用。当工作数据集能装进缓存时，两个实现的相对性能可能因 CPU 时钟频率不同而不同，因为内存不受其影响（而其他一切都受影响）。

因此，我们[建议](/hpc/profiling/noise)保持时钟频率固定，而由于睿频不够稳定，本书中的大多数基准测试都在普通的 2GHz 下运行。

### 单向访问

这个递增循环在执行过程中既需要读也需要写：每次迭代，我们取回一个值，递增它，然后写回。在许多应用中，我们只需要二者之一，所以让我们尝试测量单向带宽。

计算数组的和只需要内存读：

```c++
for (int i = 0; i < N; i++)
    s += a[i];
```

而将数组清零（或填充任何其他常量值）只需要内存写：

```c++
for (int i = 0; i < N; i++)
    a[i] = 0;
```

两个循环都被编译器平凡地[向量化](/hpc/simd)了，第二个循环实际上被替换为 `memset`，因此这里 CPU 也不是瓶颈（除非数组能装进 L1 缓存）。

![](../img/directional.svg)

单向与双向内存访问表现不同的原因在于，它们共享缓存与内存总线以及其他 CPU 设施。以内存为例，这导致纯读与同时读写两种场景之间有两倍的性能差，因为内存控制器必须在单向内存总线上切换模式，从而使带宽减半。对 L2 缓存来说，性能下降没有那么严重：这里的瓶颈不是缓存总线，所以递增循环只损失约 15%。

图上还有一个有趣的异常：当数组触及 L3 缓存和内存时，只写循环与读写循环的表现相同。这是因为 CPU 在每次访问时都会把数据搬移到最高层级的缓存，无论读还是写都是如此——这通常是个不错的优化，因为在许多使用场景中我们很快会用到它。对读数据来说这不是问题，因为数据反正要穿过缓存层级；但对写来说，这会导致紧跟写入之后又派发一次隐式读——因此需要两倍的总线带宽。

### 绕过缓存

我们可以使用*非临时*（non-temporal）内存访问来阻止 CPU 预取我们刚刚写入的数据。为此，我们需要更直接地重新实现清零循环，不依赖编译器向量化。

忽略若干特殊情况，`memset` 和自动向量化的赋值循环在底层所做的就是用 [SIMD 指令](/hpc/simd)[搬移](/hpc/simd/moving) 32 字节的数据块：

```c++
const __m256i zeros = _mm256_set1_epi32(0);

for (int i = 0; i + 7 < N; i += 8)
    _mm256_store_si256((__m256i*) &a[i], zeros);
```

我们可以把普通的向量存储内建函数替换为*非临时*版本：

```c++
const __m256i zeros = _mm256_set1_epi32(0);

for (int i = 0; i + 7 < N; i += 8)
    _mm256_stream_si256((__m256i*) &a[i], zeros);
```

非临时内存读写是一种告诉 CPU 的方式：我们以后不会再需要刚刚访问过的数据，所以写入之后没有必要把数据读回来。

![](../img/non-temporal.svg)

一方面，如果数组足够小、能装进缓存，而我们确实在其后不久访问它，这会带来负面效果，因为我们必须从头开始从内存读取它（或者，在这种情况下，我们必须*写入*内存而不是使用本地的缓存副本）。另一方面，这避免了读回，让我们能更高效地使用内存总线。

事实上，在内存场景下性能提升不止 2 倍，甚至比只读基准测试还快。这是因为：

- 内存控制器不必在总线上的读与写模式之间切换；
- 指令序列变得更简单，允许更多待处理的内存指令；
- 最重要的是，内存控制器可以简单地对非临时写请求「发射即忘」——而对于读，它需要记住数据到达后如何处理（类似于网络软件中的连接句柄）。

理论上，两种请求应该使用相同的带宽：读请求发送地址并得到数据，非临时写请求发送*带数据的*地址并什么也不得到。不考虑方向的话，我们传输的数据量相同，但读周期会更长，因为它需要等待数据被取回。由于内存系统能处理的并发请求数[存在实际上限](../mlp)，读写周期的这个延迟差异也转化为它们带宽的差异。

此外，由于这些原因，单个 CPU 核心通常[无法完全占满内存带宽](../sharing)。

同样的技巧也适用于 `memcpy`：它也只用 SIMD 加载/存储指令搬移 32 字节的块，同样可以改成非临时方式，使大数组的吞吐量翻倍。还有一个非临时加载指令（`_mm256_stream_load_si256`），用于在你想*读取*而不污染缓存时使用（例如，`memcpy` 之后你不再需要原数组，但会需要调用它之前访问过的某些数据）。
