把需要同时取回的数据放在一起通常是有益的：最好放在同一条缓存行上，如果做不到，则放在相邻的缓存行上。这能改善内存访问的[空间局部性](/hpc/external-memory/locality)，对内存受限算法的性能产生积极影响。

为了演示这样做可能带来的效果，我们修改[指针追逐](../latency)基准测试，使下一个指针不再由单个字段计算，而是由可变数量的字段（$D$）计算。

### 实验

第一种方法将这些字段集中放在一起，作为二维数组的行。我们将这种变体称为*结构体数组*（array of structures，AoS）：

```c++
const int M = N / D; // # of memory accesses
int p[M], q[M][D];

iota(p, p + M, 0);
random_shuffle(p, p + M);

int k = p[M - 1];

for (int i = 0; i < M; i++)
    q[k][0] = p[i];

    for (int j = 1; j < D; j++)
        q[i][0] ^= (q[j][i] = rand());

    k = q[k][0];
}

for (int i = 0; i < M; i++) {
    int x = 0;
    for (int j = 0; j < D; j++)
        x ^= q[k][j];
    k = x;
}
```

第二种方法则将它们分开存放。最偷懒的做法是转置二维数组 `q`，并在其后续所有访问中交换下标：

```c++
int q[D][M];
//    ^--^
```

类似地，我们称这种变体为*数组结构体*（structure of arrays，SoA）。显然，对于较大的 $D$，它的表现要差得多：

![](../img/aos-soa.svg)

两种变体的性能都随 $D$ 线性增长，但 AoS 总共需要取回的缓存行最多可少 16 倍，因为数据是顺序存放的。即使当 $D=64$ 时，处理其余 63 个值所花费的额外时间也小于第一次取回的延迟。

你还可以看到在 2 的幂处出现的尖峰。AoS 的表现略好，因为它可以用 SIMD 更快地计算[水平异或和](/hpc/simd/reduction)。相比之下，SoA 的表现要差得多，但这不是 $D$ 的问题，而是 $\lfloor N / D \rfloor$——第二个维度的大小——是较大的 2 的幂：这会造成相当复杂的[缓存组相联效应](../associativity)。

### 临时存储争用

乍一看，似乎不该有任何缓存问题，因为 $N=2^{23}$，数组本来就太大，根本放不进 L3 缓存。微妙之处在于，要并行处理来自不同内存位置的多个元素，你仍然需要一些空间来临时存储它们。你不能简单地使用寄存器，因为寄存器数量不够，所以它们必须存储在缓存中——即使在微秒之后你就不再需要它们了。

因此，当 `N / D` 是较大的 2 的幂，而我们沿着第一个下标遍历数组 `q[D][N / D]` 时，一些我们临时需要的内存地址会映射到同一条缓存行——由于那里没有足够的空间，其中许多地址将不得不从内存层次结构的更高层重新取回。

这里还有一个令人挠头的问题：如果我们启用[大页](../paging)，对于大多数 $D$ 值，总延迟按预期会降低 10-15%，但对于 $D=64$，它反而使情况糟糕了十倍：

![注意对数刻度](../img/soa-hugepages.svg)

我怀疑即便是设计内存控制器的工程师，也无法一下子解释清楚发生了什么。

简而言之，差异在于：与每个核心私有的 L1/L2 缓存不同，L3 缓存在共享该缓存的不同核心之间同步时，必须使用*物理*内存地址而不是*虚拟*地址。

当我们使用 4K 内存页时，虚拟地址在物理内存上多少是任意分散的，这使得缓存组相联问题不那么严重：物理地址将具有相同的模 4K 字节的余数，而不是虚拟地址对应的 `N / D`。当我们专门使用大页时，这个最大对齐限制增大到 2M，缓存行受到的争用大大增加。

这是我所知的唯一一个启用大页反而使性能变差的例子，更不用说差十倍了。

### 填充式 AoS

只要取回的缓存行数量相同，它们位于哪里并不重要，对吧？让我们来验证一下，在 AoS 代码中改用[填充整数](../cache-lines)：

```c++
struct padded_int {
    int val;
    int padding[15];
};

const int M = N / D / 16;
padded_int q[M][D];
```

除此之外，我们仍然在计算 $D$ 个填充整数的异或和。我们恰好取回 $D$ 条缓存行，但这次是顺序取回。运行时间本应与 SoA 无异，但实际并非如此：

![](../img/aos-soa-padded.svg)

对于 $D=63$，运行时间大约降低了 ⅓，但这只适用于超过 L3 缓存大小的数组。如果我们固定 $D$ 并改变 $N$，可以看到在较小的数组上，填充版本的表现反而略差，因为随机[缓存共享](../cache-lines)的机会更少：

![](../img/aos-soa-padded-n.svg)

由于较小数组上的性能不受影响，这显然与内存（RAM）的工作原理有关。

### 内存特有的时序

从性能分析的角度看，内存中的所有数据物理上都存储在一个由微小电容单元组成的二维数组中，该数组被划分为行和列。要读写任意单元，你需要执行一、二或三个动作：

1. 将一行的内容读入*行缓冲器*（row buffer），这会暂时使电容器放电。
2. 读写该缓冲器中的某个特定单元。
3. 将行缓冲器的内容写回电容器，以便数据得以保留，行缓冲器可以用于其他内存访问。

关键点在这里：对于对应同一行的两次内存访问之间，你不必执行步骤 1 和 3——你可以直接把行缓冲器当作临时缓存。这三个动作花费的时间大致相同，因此这种优化使长序列的同行局部访问比分散的访问模式快三倍。

![](../img/ram.png)

行的大小因硬件而异，但通常在 1024 到 8192 字节之间。因此，即使填充式 AoS 基准测试将每个元素放在单独的缓存行中，它们仍然很可能位于同一内存行上，整个读取序列的运行时间大约只有原来的三分之一，再加上第一次内存访问的延迟。
