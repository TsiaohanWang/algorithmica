在[指针追逐基准测试](../latency)中，为了简单起见，我们没有使用真正的指针，而是使用相对于基地址的整数下标：

```c++
for (int i = 0; i < N; i++)
    k = q[k];
```

x86 的[内存寻址运算符](/hpc/architecture/assembly#addressing-modes)与地址计算融合在一起，因此 `k = q[k]` 这一行折叠成一条简练的指令，它在底层同时完成了乘以 4 和加法：

```nasm
mov rax, DWORD PTR q[0+rax*4]
```

虽然完全融合了，但这些额外的计算仍然会给内存操作增加一些延迟。L1 取回的延迟是 4 或 5 个周期——如果我们需要对地址进行复杂计算，就是后者。因此，排列基准测试测得每次跳跃 3ns 或 6 个周期：读取和地址计算各占 4+1，再加上一次将结果移动到正确寄存器的操作。

### 指针

如果我们把「伪指针」——下标——替换为真正的指针，可以让基准测试跑得稍快一些。

让「指向指针的指针的指针……」这种构造工作会有一些语法上的麻烦，所以我们将定义一个结构体，它只包装一个指向自身类型的指针——大多数指针追逐本来就是这样实现的：

```cpp
struct node { node* ptr; };
```

现在我们用指针随机填充数组并追逐它们：

```cpp
node* k = q + p[N - 1];

for (int i = 0; i < N; i++)
    k = k->ptr = q + p[i];

for (int i = 0; i < N; i++)
    k = k->ptr;
```

对于能装进 L1 缓存的数组，这段代码现在运行在 2ns / 4 个周期。为什么不是 4+1=5？因为 Zen 2 [有一个有趣的特性](https://www.agner.org/forum/viewtopic.php?t=41)，允许仅通过地址访问的数据实现零延迟重用，所以这里的「移动」是透明的，总共节省了两个周期。

不幸的是，在 64 位系统上它有一个问题：指针的大小翻倍，使数组比使用 32 位下标时更早溢出缓存。延迟对大小的图形看起来就像向左平移了一个 2 的幂——完全符合预期：

![](../img/permutation-p64.svg)

切换到 32 位模式可以缓解这个问题：

![](../img/permutation-p32.svg)

要在一台本世纪制造的计算机上跑起来，你需要[费一番周折](https://askubuntu.com/questions/91909/trouble-compiling-a-32-bit-binary-on-a-64-bit-machine)搞到 32 位库，但除非你需要与 64 位软件交互或访问超过 4G 的内存，这不会带来其他问题。

### 位域

在较大的问题规模上，性能受内存而非 CPU 限制，这一事实让我们可以尝试一些更奇怪的做法：我们可以用少于 4 字节来存储下标。这可以通过[位域](../alignment#bit-fields)实现：

```cpp
struct __attribute__ ((packed)) node { int idx : 24; };
```

除了为位域定义一个结构体，你不需要做任何其他事情——编译器会自行处理这 3 字节的整数：

```cpp
int k = p[N - 1];

for (int i = 0; i < N; i++) {
    k = q[k].idx = p[i];

for (int i = 0; i < N; i++) {
    k = q[k].idx;
```

这段代码在 L1 缓存上测得为 6.5ns。还有一些改进空间，因为编译器选择的默认转换流程不是最优的。我们可以手动加载一个 4 字节的整数并自己截断它（我们还需要给 `q` 数组多添加一个元素，以确保我们拥有那额外的一个字节内存）：

```cpp
k = *((int*) (q + k));
k &= ((1<<24) - 1);
```

现在它运行在 4ns，并产生下图：

![](../img/permutation-bf-custom.svg)

如果你凑近仔细看（[该图是 svg](../img/permutation-bf-custom.svg)），你会发现指针在很小的数组上胜出，然后从大约 L2-L3 缓存边界开始，我们自定义的位域接管，而对于非常大的数组这无关紧要，因为我们反正永远也命中不了缓存。

这不是那种能带来 5 倍提升的优化，但当所有其他资源都用尽时，它仍然值得一试。
