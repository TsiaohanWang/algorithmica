---
title: 缓存行
weight: 3
---

CPU 缓存系统中数据传输的基本单位不是单个比特或字节，而是*缓存行*（cache line）。在大多数架构上，缓存行的大小是 64 字节，这意味着所有内存都被划分为 64 字节的块，每当你请求（读或写）单个字节时，无论你是否需要，你都会同时取回其 63 个缓存行邻居。

为了演示这一点，我们给[递增循环](../bandwidth)添加一个「step」参数。现在我们只碰每个第 $D$ 个元素：
 
```cpp
for (int i = 0; i < N; i += D)
    a[i]++;
```

如果我们用 $D=1$ 和 $D=16$ 运行它，可以观察到一些有趣的现象：

![性能按运行基准测试的总时间归一化，而非按递增的元素总数](../img/strided.svg)

随着问题规模的增长，两个循环的曲线汇合在一起，尽管其中一个做的工作量是另一个的 16 分之一。这是因为就缓存行而言，两个循环取回的内存完全相同，跨步循环其实只需要其中十六分之一的事实无关紧要。

当数组能装进 L1 缓存时，跨步版本完成得更快——虽然不是 16 倍，而只是 2 倍。这是因为它只需要做一半的工作：每 16 个元素只执行一条 `inc DWORD PTR [rdx]` 指令，而原始循环处理同样的 16 个元素需要两条 8 元素的[向量指令](/hpc/simd)。两种计算都受限于把结果写回：Zen 2 每个周期只能写回一个字——无论这个字是由一个整数还是八个整数组成。

当把步长参数改为 8 时，两条曲线持平，因为现在每 16 个元素我们也需要两次递增和两次写回：

![](../img/strided2.svg)

我们可以利用这个效应来最小化[延迟基准测试](../latency)中的缓存共享，从而更精确地测量它。我们需要*填充*（pad）排列的下标，使每个下标都位于自己的缓存行内：

```c++
struct padded_int {
    int val;
    int padding[15];
};

padded_int q[N / 16];

// constructing a cycle from a random permutation
// ...

for (int i = 0; i < N / 16; i++)
    k = q[k].val;
```

现在，当我们循环一圈再次请求某个下标时，它更有可能已被踢出缓存：

![](../img/permutation-padded.svg)

设计和分析内存受限算法时一个重要的实践教训是：统计访问的缓存行数量，而不只是内存读写操作的总次数。
